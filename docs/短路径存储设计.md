# 短路径存储设计

## 问题与改造范围

证据路径曾同时嵌套安装根、Host 登记身份、运行、VM、步骤和执行尝试，完整身份被重复写入目录。
此外，Host 曾直接用 Guest Artifact 目标路径存储文件，导致不同 VM 的同名目标互相冲突。

本次已实现两处物理布局调整：Host 按不可变清单序号保存 Artifact，Guest 将每次执行的证据移到安装根下的
独立尝试目录。完整身份保存在元数据中，不采用截断 UUID 或另外分配短编号的映射服务。

任务仍是 schema 3，运行清单仍是 schema 2、`protocol_version=4`，执行结果仍是 schema 2。
用户指定的 Artifact 目标、执行路径、收集路径和 Host 规范结果路径不变。

## Host Artifact 隔离

新运行的 Host 内部文件布局为：

```text
runs/<run-id>/
  task.json
  .artifacts/0.bin
  .artifacts/1.bin
```

文件名是清单 `artifacts` 数组的零起序号。清单在原子发布后不可变，序号与清单中 VM、逻辑目标路径及
SHA-256 的对应关系也保持不变。网关先验证请求所属 VM 和逻辑路径，再取得相应物理文件。

因此两台 VM 都可以声明 `artifacts/preflight.ps1`，同内容或不同内容均可；同一 VM 重复声明相同目标仍被
拒绝。Guest 下载后仍使用 `artifacts/preflight.ps1`，无需知道 `.artifacts` 或序号。

旧运行没有 `.artifacts` 时，按原来的 `artifacts/...` 读取。存在 `.artifacts` 的新运行若缺少某个文件，
直接报告缺件，不逐文件回退旧目录，避免读取错误副本。旧运行不搬迁、不改写清单。

## Guest 证据目录

新尝试使用：

```text
<storage_root>/staging/<job-id>/
  attempt.json
  stdout.log.partial
  stderr.log.partial
  stdout.log
  stderr.log
  files/<collect_files 中的相对路径>
  diagnostic.json       # 出错时保留
  execution.json        # 出错时保留的本地结果，不是 Host 完成标志
```

与旧证据路径相比，去掉了 `mirror/enrolled/<Host>/runs/<run>/results/<VM>/<step>/.jobs` 这组外层目录。
`files` 层保留，用来区分收集文件与本次尝试的日志、身份及诊断文件。

下例使用虚构标识，长度与问题现场相同：

```text
旧（266 字符）：
C:\ProgramData\SatsumaTestLab\mirror\enrolled\host-20260101000000-0123456789abcdef\runs\example-preflight-20260101-0000\results\vm-00000000-0000-0000-0000-000000000001\gateway_preflight\.jobs\job-20260101000000-0123456789abcdef\files\artifacts\gateway\preflight.json

新（112 字符）：
C:\ProgramData\SatsumaTestLab\staging\job-20260101000000-0123456789abcdef\files\artifacts\gateway\preflight.json
```

这里的 154 字符缩减是布局计算，不是对所有任务路径长度的保证。用户自己的相对路径仍可能很长，文件访问
层必须继续支持扩展 Win32 路径，覆盖生成、复制、大小/哈希计算、流式打开、上传下载和删除。
扩展路径前缀只在文件 API 边界使用，不写入任务或配置，不修改系统长路径注册表设置。

`attempt.json` 使用 `schema_version=1`、`layout_version=1`，记录 `lab_id`、`enrollment_id`、
`hardware_id`、`run_id`、`vm_id`、`step_id`、`job_id`、`attempt` 和创建时间。排错时从此文件恢复完整归属，
不能仅凭目录名推断业务身份。每个尝试目录独占创建，已存在目录不会被覆盖；staging 由 SYSTEM 和
Administrators 管理，普通用户不能写入。

SYSTEM 进程的日志直接写入新尝试目录。业务工作目录仍按运行共享，保留多步骤文件传递；交互用户日志仍
使用原工作目录和既有 ACL，结束后复制到证据区。不会为了缩短路径而破坏交互身份或改变程序工作目录。
第三方脚本自身的文件 API 仍可能有路径限制，需要与 Agent 上传链路的长路径能力分别验证。

Host 最终结果仍位于 `runs/<run-id>/results/<vm-id>/<step-id>/`，保持报告可读性和旧工具兼容。
成功发布且不需要留证时，Agent 只清理自身创建的新尝试目录；收集、上传或所有权异常保留现场。
旧 `.jobs` 不迁移、不自动删除，业务工作目录仍按任务 cleanup 策略处理。

## 错误报告与恢复

收集或上传失败保留本地原日志、`execution.json` 和 `diagnostic.json`。诊断分别记录 `process_status`、
实际 `exit_code`、`evidence_status` 和发布状态，避免把“程序成功但上传失败”误判为业务执行失败。

上传异常时只在原 claim 内尝试补发失败摘要，不重新执行程序。摘要使用现有结果 schema，`stdout`、
`stderr` 为空，`files` 为空数组，已经取得的退出码保留。网关仍检查 job、attempt、owner 和有效期；
完全失联或失权时不能发布规范结果，`retry_safe=false` 的人工门禁继续生效。

Host `report.agent_errors` 汇总旧 `invalid_run` 和新 `step_errors`；诊断文件不代替规范 `execution.json`。
有错误但结果不齐时，报告为 `status=failed`、`complete=false`。`report --wait-seconds` 提前返回
`wait_status=agent_error`、退出码 1，帮助操作者及时看见错误；它不释放租约，编排仍等待完整结果或人工门禁。

恢复前保存报告、claim 和本地尝试证据，核对实际业务状态与 claim owner。已有全部规范结果、原 Host 已退出
且租约属于该运行时，才可使用 `runs finalize`；编排恢复使用带原 run ID 和 lifecycle 的原计划执行
`lab recover --plan`。`lab unlock --force true` 只放弃实验室租约，不补齐结果或解除步骤门禁。
不得手工删除 claim、更改 `retry_safe` 或把本地结果伪装成规范结果，详见[运行管理](用户指南.md#运行管理)。

## 验收与实施记录

实现包括 Host 存储映射、Guest 尝试目录、文件 API 长路径处理、失败摘要和诊断汇总，以及发行构建身份。
发行包通过 `BUILD-INFO.md` 和 `release-manifest.json` 展示实际提交、dirty 状态及文件哈希，避免同版本
不同构建混用；构建身份不改变升级版本优先级。

验收覆盖跨 VM 同名同/不同内容、同 VM 重复拒绝、旧运行读取、长路径读写和上传下载、尝试归属与隔离、
证据失败保留、失权 fencing、非安全步骤门禁及发行清单一致性。自动测试和真实 VM 测试的执行结果以本次
`build/` 下的测试日志、隔离 VM 测试证据及最终发行验收报告为准；本文记录实现设计，不将待执行用例标为通过。
