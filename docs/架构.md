# 架构

## 目标与边界

Satsuma 将“控制虚拟机生命周期”和“在 Guest 内执行测试”分成两个进程，并使用 Shared Folder 连接它们。
设计目标是让 Host 或 Agent 被强制终止后仍能根据磁盘证据继续判断，而不是依赖常驻连接中的内存状态。

系统只面向可信本机实验室。它不会对 Artifact 做安全沙箱、代码签名验证或租户权限隔离。执行未知或不可信
程序时，应使用单独的受控基础设施和网络边界。

## 组件

| 组件 | 职责 | 不负责 |
|---|---|---|
| `SatsumaHost` | 独占实验室、校验环境、控制 VMware、发布任务、归档清理、汇总报告 | 在 Host 执行业务 Artifact |
| `SatsumaVM` | 以 Windows Service 运行，上报 inventory、执行进程树、写回证据和清理确认 | 控制其他 VM 或监听网络端口 |
| Shared Folder | 保存任务、Artifact、claim、日志、结果和 Agent presence | 提供事务数据库或访问控制 |
| `vmrun` | 启停 VM、恢复/创建/删除快照、查询 VMware 状态 | 传输任务或业务结果 |

Host 库、VM 库与核心文件协议模型分开构建，两个可执行文件只是 CLI/Service 入口。生产依赖只有 Windows
系统库和固定版本的 `nlohmann/json`。

Agent 身份分为两层：SMBIOS `hardware_id` 是克隆后变化的物理寻址键，`vm_id` 是任务计划使用的稳定业务角色。
Agent 按硬件键发布 presence；Host 在 `lab` 配置和 Shared Folder 绑定记录中维护两者映射。旧 Agent 配置仍可
显式声明 `vm_id`，但不会省略硬件身份。

## 主流程

```text
task.json + Artifact
        |
        v
SatsumaHost --原子发布--> shared/runs/<run-id>/task.json
        |                              |
        | vmrun                        | 扫描、claim、续租
        v                              v
     VMware VM                    SatsumaVM Service
                                       |
                                       | Job Object / 交互用户 helper
                                       v
                                  Guest 本机进程
                                       |
                                       v
shared/runs/<run-id>/results/.../execution.json
        |
        v
SatsumaHost report/orchestrate
```

Host 先在 `.preparing-*` 目录复制并校验 Artifact，最后整体改名为正式运行目录。Agent 不扫描点号前缀目录，
因此不会看到半发布任务。

Host 写操作先取得按 `lab_id` 和配置路径区分的 Win32 Mutex，再维护归档目录中的持久租约。进程锁关闭创建
竞态，租约跨越 Host 退出和崩溃，防止旧 Guest 任务仍运行时第二个使用者进入 VMware 操作。只读 status、
report 和 inventory 查询不取得写租约。

## 可靠性模型

### Claim 与 fencing

每个 `<vm-id>/<step-id>` 只有一个规范 claim。Agent 领取时写入 `job_id`、`session_id`、`boot_id`、租约时间
和 attempt；长任务通过不可变续租 sidecar 延长租约。结果发布前会在同一锁事务中再次核对所有权：失去
claim 的旧进程只能留下 `.jobs/<job-id>` 取证文件，不能覆盖规范结果。

`retry_safe=true` 的步骤可在租约过期后重放。对于无法证明幂等的步骤，过期 claim 会生成
`manual_intervention_required` 门禁，由人确认外部状态后处理。

### 进程与故障隔离

普通执行使用 Windows Job Object，超时、取消、日志超限或 Service 停止会终止完整进程树。交互执行由
LocalSystem Service 在活动控制台用户会话中启动同一个 `SatsumaVM.exe` helper，并保持相同的 Job Object
清理语义。

Agent 按运行目录隔离异常。损坏或不兼容的运行会写入 `<vm-id>-agent-error.json`，随后继续扫描其他运行。
单个任务不会使整个 Service 文件循环退出。

### 取消与保留

Host 通过原子写入 `cancel.json` 请求取消。正在执行的 Agent 最多约 100ms 后触发停止令牌；尚未执行的步骤
也会得到稳定失败结果。取消不是删除，完整证据仍保留给 `report`。

`runs prune --keep N` 按运行目录最近修改时间保留最新 N 个，只删除超过保留数且报告已完整的运行。未完成、
人工门禁或无法解析的目录不会自动删除。

## 生命周期编排

`orchestrate` 使用任务中的 `lifecycle.vms` 顺序执行：

1. 可选恢复每台 VM 的指定快照。
2. 按声明顺序启动 VM 并等待 Agent presence。
3. 原子发布主任务并等待完整报告。
4. 复制并逐文件校验 Host 归档，执行 `lifecycle.finally`。
5. 按 `cleanup` 请求 Agent 删除 Guest 工作目录，并在允许时删除已归档的共享运行目录。
6. 根据业务成功或失败按逆序执行 `leave_running`、`stop` 或 `restore`。

每次阶段转换写入 Host 归档目录的 `lifecycle.json`。Host 重启后可根据该文件继续或完成清理；若状态不能
安全推断，则输出人工介入状态，而不是猜测外部系统是否已执行。

## 存储边界

Shared Folder 是协议事实源，Host `archive_root` 保存编排状态、持久租约和证据副本。Guest 安装器优先选择
合适的 `D:\SatsumaTestLab`，否则使用 `%ProgramData%\SatsumaTestLab`；`agent/` 只允许 SYSTEM 和
Administrators 修改，`work/<lab-id>/<run-id>/<vm-id>` 由 SYSTEM 与经验证的交互用户按运行共享。

Agent 不再在步骤完成后静默删除目录。Host 归档成功后发布清理请求，Agent 终止 Job Object、删除本次工作
目录并写回清理结果。Host 只在确认成功后继续删除共享运行；错误进入恢复失败并保留实验室租约。恢复快照的
VM 可由快照直接回退本地目录，但 Host 归档、Shared Folder 和外部系统不会随 Guest 快照回滚。

每个 Agent 进程在首次成功访问文件通道时采集一次 Windows、架构、脚本 engine、固定盘和内存 inventory。
presence 仅引用快照摘要；普通轮询不重复系统探测，文件丢失或篡改时从会话缓存自愈。

默认限制包括：每次运行最多 256 个 Artifact 和 256 个步骤；单 Artifact 2 GiB；单步骤最多 256 个参数、
128 个收集文件；单文件 512 MiB、收集总量 2 GiB；stdout 与 stderr 合计 64 MiB。

## 安全假设

- `lab.json`、Agent 配置、任务计划和 Artifact 由可信操作者提供。
- Shared Folder 仅暴露给参与实验的 Host/Guest，不作为跨租户交换目录。
- Host 只控制 `lab.json` 明确列出的 VMX 和快照；真实故障注入目标默认不生成。
- Agent Service 以 LocalSystem 运行，任务默认也以 SYSTEM 运行。需要用户配置文件或桌面资源时必须显式使用
  `interactive_user`，并保证活动控制台用户保持登录。
- SHA-256 用于传输完整性与串属验证，不代表发布者身份。生产供应链仍应在 Satsuma 外部验证代码签名。
