# 用户指南

## 环境要求

Host：

- Windows 10 或 Windows 11 x64。
- VMware Workstation，且 `vmrun.exe` 可用。
- 一个只用于实验的本机目录，作为 VMware Shared Folder 的 Host 路径。

Guest：

- Windows 10 或 Windows 11 x64。
- 已安装并运行 VMware Tools。
- 已启用 Shared Folder，并能访问 `\\vmware-host\Shared Folders\<共享名>`。
- 安装 Agent 时可取得管理员权限。

普通 NAT/DHCP 网络即可。Satsuma 的任务与状态通道不需要固定 IP、端口放行或 Host/Guest 互连网络。

## 准备 Host

发布包解压后包含 `bin`、`examples`、`schemas`、`scripts` 和 `docs`。源码构建的 Release 二进制位于
`build/windows-default/bin/Release`。

将根目录 `lab.json` 复制为 `lab.local.json`，然后修改以下字段：

| 字段 | 含义 |
|---|---|
| `lab_id` | 当前实验室的稳定标识，只允许字母、数字、下划线和连字符 |
| `provider.vmrun` | `vmrun.exe` 的绝对路径 |
| `host.archive_root` | Host 编排状态与归档证据目录 |
| `shared_folder.host_root` | VMware Shared Folder 对应的 Host 绝对路径 |
| `vms[].id` | VM 稳定标识，必须与 Guest Agent 配置一致 |
| `vms[].vmx` | VMX 文件绝对路径 |
| `vms[].agent_version` | Host 期望的 Agent 版本 |
| `vms[].snapshots` | 基础快照、Satsuma 创建快照的前缀和配额 |

配置加载器会拒绝未知字段、相对运行路径和重复 VM ID。不要把仓库模板中的示例路径直接用于真实环境。

## 安装 Guest Agent

1. 在 Host 的 Shared Folder 根目录创建 `satsuma-bootstrap`。
2. 将 Release `SatsumaVM.exe`、`scripts/install-agent.ps1` 和 Agent 配置复制到该目录。
3. 将 Agent 配置命名为 `agent.json`，并设置与 `lab.local.json` 相同的 `lab_id` 和 VM `id`。
4. 在 Guest 管理员 PowerShell 中从共享目录运行安装脚本。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "\\vmware-host\Shared Folders\vm-share\satsuma-bootstrap\install-agent.ps1"
```

安装脚本会请求 UAC，把二进制和配置复制到 `C:\Satsuma`，创建 LocalSystem 自动启动 Service，并清理早期
版本遗留的同名计划任务。重复执行用于升级安装文件；脚本不会从网络下载内容。

Agent 配置字段：

| 字段 | 含义 |
|---|---|
| `protocol_version` | 当前生产协议固定为 `2` |
| `shared_root` | Guest 看到的 Shared Folder UNC 绝对路径 |
| `local_work_root` | SYSTEM 步骤的 Guest 本机工作目录 |
| `poll_interval_ms` | 正常扫描间隔，100 到 60000 ms |
| `reconnect_interval_ms` | Shared Folder 不可用时的重试间隔 |

可先在 Guest 前台验证配置：

```powershell
C:\Satsuma\bin\SatsumaVM.exe --config C:\Satsuma\agent.json --validate-config
```

## 首次验收

先确认 VM 已启动且 Service 正常，再在 Host 运行：

```powershell
bin\SatsumaHost.exe check --config lab.local.json --vm client --timeout-seconds 180
```

`status=ready` 表示 VMware、共享目录、Agent presence 和文件往返探针均通过。`degraded` 通常表示 Agent 尚未
上线或 VMware Tools 暂未就绪；`failed` 表示配置、共享目录或 VMware 控制不可用。

下发无 Artifact 的最小任务：

```powershell
bin\SatsumaHost.exe run --config lab.local.json --plan examples\hello-vm-task.json
```

记录输出的 `run_id`，再等待报告：

```powershell
bin\SatsumaHost.exe report --config lab.local.json --run <run-id> --wait-seconds 300
```

## 编写任务

任务计划必须符合 `schemas/task.schema.json`。`echo` 用于链路探针；`execute` 的 `program` 必须对应同一 VM
登记的 Artifact 目标，不能执行 Guest 上未登记的任意绝对路径。

```json
{
  "$schema": "../schemas/task.schema.json",
  "schema_version": 1,
  "name": "installer smoke",
  "artifacts": [
    {
      "source": "D:\\build\\Installer.exe",
      "vm": "client",
      "shared_destination": "artifacts/client/Installer.exe"
    }
  ],
  "steps": [
    {
      "id": "install",
      "vm": "client",
      "type": "execute",
      "program": "artifacts/client/Installer.exe",
      "arguments": ["/quiet", "/norestart"],
      "run_as": "system",
      "retry_safe": false,
      "timeout_seconds": 600,
      "collect_files": ["logs/install.log"]
    }
  ]
}
```

`source` 必须是 Host 绝对文件路径。`shared_destination` 必须位于 `artifacts/` 下。Artifact 在发布前后都会
计算 SHA-256；可额外提供 `sha256` 作为期望值。

`retry_safe` 只应为可证明幂等的步骤设为 `true`。安装、刷写和外部系统写操作通常应保持 `false`，避免
Agent 崩溃后自动重复执行不确定操作。

## 运行身份

`system` 是默认且推荐的自动化身份，由 LocalSystem Service 直接启动。任务需要当前用户配置文件、桌面
会话或只能在交互用户下工作的程序时，显式使用 `interactive_user`。

交互执行要求 Guest 存在活动控制台用户且执行期间身份不变化。无活动 Session、用户切换或 helper 身份校验
失败都会生成失败结果，不会自动回退到 SYSTEM。

## 多 VM 编排

带 `lifecycle` 的计划必须使用 `orchestrate`，并显式给出不会重复的 `run_id`。参考
`examples/multi-vm-task.json`：

```powershell
bin\SatsumaHost.exe orchestrate --config lab.local.json --plan examples\multi-vm-task.json --timeout-seconds 900
```

`restore_before` 在执行前恢复快照；`on_success` 和 `on_failure` 分别定义业务成功/失败后的 VM 动作。清理按
VM 声明顺序的逆序执行。`finally` 步骤无论主任务结果如何都会尝试执行。

## 运行管理

```powershell
bin\SatsumaHost.exe runs list --config lab.local.json
bin\SatsumaHost.exe runs cancel --config lab.local.json --run <run-id> --reason "operator request"
bin\SatsumaHost.exe runs prune --config lab.local.json --keep 20
```

取消会终止正在运行的进程树并保留失败证据。`prune` 只删除保留数之外、已收到全部规范结果的运行；pending、
invalid 和人工门禁运行会保留。

## Agent 更新与身份迁移

更新会把候选二进制发布到 Shared Folder，Agent 校验大小和 SHA-256 后停止 Service、切换文件、重启并验证
新 presence。失败会尝试恢复旧二进制和配置。

```powershell
bin\SatsumaHost.exe agent update --config lab.local.json --vm client --binary .\SatsumaVM.exe --version 0.1.1 --timeout-seconds 300
```

把克隆 VM 的 Agent 从旧 ID 迁移到 `lab.json` 中另一个空闲 ID：

```powershell
bin\SatsumaHost.exe agent rebind --config lab.local.json --vm client --next-vm client-2 --binary .\SatsumaVM.exe --version 0.1.1 --timeout-seconds 300
```

目标 ID 已存在 presence 时迁移会被拒绝，防止两台 VM 共用身份。

## 退出码

| 命令结果 | 退出码 |
|---|---:|
| 成功或未等待的 pending 报告 | 0 |
| 业务失败或普通运行错误 | 1 |
| 命令行参数错误 | 2 |
| 检查 degraded 或等待超时 | 3 |
| 需要人工介入 | 5 |

自动化应同时检查退出码和 JSON 顶层 `status`。未使用 `--wait-seconds` 的 `report` 返回 `pending` 时退出码为
0，表示查询本身成功，并不表示任务已完成。

## 排障

- `check` 失败：先核对 `vmrun`、VMX 和 Shared Folder 的 Host/Guest 两侧路径。
- Agent 不上线：在 Guest 检查 `Get-Service SatsumaVM`，再前台运行 `--validate-config`。
- 某个运行为 `invalid`：检查该目录的 `task.json` 和 `state/<vm>-agent-error.json`；其他运行仍会继续。
- `manual_intervention_required`：先核对被测程序和外部系统状态，不要直接删除 claim 或伪造结果。
- 日志超限：步骤会失败并终止进程树；减少输出或改为写入有明确容量约束的收集文件。
- 磁盘增长：定期执行 `runs prune`，并为 Host 归档目录设置独立的组织级保留策略。
