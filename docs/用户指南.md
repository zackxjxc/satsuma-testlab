# 用户指南

## 环境要求

Host：

- Windows 10 或 Windows 11 x64。
- VMware Workstation，且 `vmrun.exe` 可用。
- 一个只用于实验的本机目录，作为 `transport.state_root`。

Guest：

- Windows 10 或 Windows 11 x64。
- 已安装并运行 VMware Tools。
- VMware VMCI 驱动可用（通常随 VMware Tools 安装）。
- 安装 Agent 时可取得管理员权限。

Guest 可以禁用或卸载网卡，也可以启用 VPN。VMCI 不经过 Guest 网络栈，不需要 IP、DNS、路由或防火墙放行。

## 通过 AI 使用

GitHub Release 发行包根目录包含 `AI-START-HERE.md`，并携带与当前二进制配套的
[`satsuma-testlab` Skill](../skills/satsuma-testlab/SKILL.md)。把整个解压目录提供给能够读取本地文件和执行
终端命令的 AI 代理，并要求它先读取 `AI-START-HERE.md`。Skill 会在首次配置、任务编写和运行恢复等不同场景
按需加载参考资料，不要求用户把整份手册复制进提示词。

支持 Agent Skills 的客户端可以把整个 `skills/satsuma-testlab/` 目录安装到其 Skill 目录；具体安装位置以
客户端文档为准。Codex 用户可以安装到 `$CODEX_HOME/skills`，未设置 `CODEX_HOME` 时使用
`%USERPROFILE%\.codex\skills`。也可以不安装，直接让 AI 读取发行包中的 `SKILL.md`。

Skill 和二进制必须来自同一发行版本。升级发行包后，同时替换已安装的 Skill；开始操作前让 AI 运行
`SatsumaHost.exe --version` 和 `SatsumaVM.exe --version` 完成兼容的语义版本核对。使用 `--version --json`
还可查询 GitHub Actions Build Number、Run Attempt 和 Git Commit；普通 `--version` 仍只输出语义版本，便于
旧脚本继续把它传给 `agent update --version`。

## 准备 Host

发布包解压后包含 `bin`、`config`、`examples`、`schemas`、`scripts` 和 `docs`。源码执行
`SatsumaPackage` 后会在根目录 `output` 生成相同的展开目录和 ZIP。

已有 VM 和基础快照时，可用 `SatsumaHost init` 根据选定的 VMX 生成 `lab.local.json`，自动填入中性 VM ID、
硬件 UUID 和发行包内 Agent 的 SHA-256。初始化不会启动 Host 网关或 VM，消费者使用时自行启动并完成 `check`。
命令和交付方式见[首次配置](首次配置.md)。

也可以将 `config/lab.template.json` 复制为 `config/lab.local.json`，然后修改以下字段。完整职责和环境发现流程见
[首次配置](首次配置.md)。

| 字段 | 含义 |
|---|---|
| `lab_id` | 当前实验室的稳定标识，只允许字母、数字、下划线和连字符 |
| `provider.vmrun` | `vmrun.exe` 的绝对路径 |
| `host.archive_root` | Host 编排状态与归档证据目录 |
| `transport.state_root` | Host 权威传输状态的本机绝对路径 |
| `transport.vmci_port` | Host VMCI 网关端口；必须与 Agent 一致 |
| `vms[].id` | 中性的 VM 资源标识；新 Guest 从 Host 接收绑定，业务角色由消费者映射 |
| `vms[].vmx` | VMX 文件绝对路径 |
| `vms[].hardware_id` | 可选 SMBIOS UUID；首次发现绑定后由 Host 写入 |
| `vms[].agent_version` | Host 期望的 Agent 版本 |
| `vms[].agent_sha256` | 可选；Host 期望的精确 Agent 二进制 SHA-256 |
| `vms[].snapshots` | 基础快照、Satsuma 创建快照的前缀和配额 |

配置加载器会拒绝未知字段、相对运行路径和重复 VM ID。模板中的 `REQUIRED` 和 `replace_with` 值必须全部
替换，不能直接用于真实环境。

## 安装 Guest Agent

1. 仅将 `bin/SatsumaVM.exe` 和 `scripts/install-agent.ps1` 复制到 Guest 同一目录。
2. 执行 `./install-agent.ps1` 或右键“使用 PowerShell 运行”，确认 UAC。无需提前提供 JSON 或启动 Host。
3. 脚本生成本机配置，使用默认 CID `2`、端口 `42510`，安装并启动服务，等待 Host 登记。
4. 完成或失败后按 Enter 关闭窗口。自动化调用加脚本参数 `-NonInteractive`。

若脚本启动前被执行策略拦截，使用 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\install-agent.ps1`。
脚本内部可处理提权，但无法在自己尚未执行时解除策略拦截。没有 BAT 入口。

安装脚本会请求 UAC。若本地固定 D 盘可写且至少有 2 GiB 可用空间，安装根为 `D:\SatsumaTestLab`；否则
回退到 `%ProgramData%\SatsumaTestLab`。脚本创建 `agent/bin`、`agent/agent.json` 和 `work`，只授予 SYSTEM 与
Administrators 全局完全控制，并清理早期版本遗留的同名计划任务。重复执行用于升级或通过显式
`-InstallRoot` 迁移旧目录；脚本不会从网络下载内容。迁移后应重新制作或更新基础快照。
安装输出中的 Service 启动类型必须为 `Auto`。完成硬件绑定和完整 `check` 后，正常关闭 VM 并重新制作基础
快照，确保冷快照包含当前版本的 Service。

Agent 配置字段：

| 字段 | 含义 |
|---|---|
| `protocol_version` | 可省略，默认使用程序支持的协议 `4` |
| `lab_id` | 省略时自动登记，由 Host 下发；显式填写保留旧式固定实验室模式 |
| `vm_id` | 可选的已绑定 VM 标识；新安装省略并通过 Host 绑定 |
| `transport.host_cid` | Host 的 VMCI Context ID，默认 `2` |
| `transport.vmci_port` | 可省略，默认 `42510`；必须与 Host 一致 |
| `transport.request_timeout_ms` | 单次 VMCI 请求超时 |
| `storage_root` | 安装器选定的本机固定盘根；不作为日常参数 |
| `mirror_root` | Guest 本地 VMCI 镜像；安装器固定为 `<storage_root>\mirror` |
| `poll_interval_ms` | 正常扫描间隔，100 到 60000 ms |
| `reconnect_interval_ms` | VMCI 网关不可用时的重试间隔 |

可先在 Guest 前台验证配置：

```powershell
D:\SatsumaTestLab\agent\bin\SatsumaVM.exe --config D:\SatsumaTestLab\agent\agent.json --validate-config
```

网络盘、可移动盘和桌面均不能作为 `storage_root`。

## 首次验收

先在 Host 独立终端启动常驻网关，再确认 VM 已启动且 Service 正常，发现 SMBIOS UUID 并完成 VM 标识绑定：

```powershell
bin\SatsumaHost.exe gateway --config config\lab.local.json
```

保持网关运行，在另一个 Host 终端执行：

```powershell
bin\SatsumaHost.exe discover --config config\lab.local.json
bin\SatsumaHost.exe agent rebind --config config\lab.local.json --vm vm_01 --hardware-id <uuid>
bin\SatsumaHost.exe check --config config\lab.local.json --vm vm_01 --timeout-seconds 180
```

`status=ready` 表示 VMware、VMCI、Agent presence 和文件往返探针均通过。`degraded` 通常表示 Agent 尚未
上线、网关未运行或 VMware Tools 暂未就绪；`failed` 表示配置、Host 状态根或 VMware 控制不可用。

`check` 会先验证或显式刷新 Guest inventory，再发布内部 echo。可以只读查看完整快照，或要求重新采集：

```powershell
bin\SatsumaHost.exe agent inventory --config config\lab.local.json --vm vm_01
bin\SatsumaHost.exe agent inventory refresh --config config\lab.local.json --vm vm_01 --timeout-seconds 180
```

下发无 Artifact 的最小任务：

```powershell
bin\SatsumaHost.exe run --config config\lab.local.json --plan examples\hello-vm-task.json
```

记录输出的 `run_id`，再等待报告：

```powershell
bin\SatsumaHost.exe report --config config\lab.local.json --run <run-id> --wait-seconds 300
```

## 编写任务

任务计划必须符合 `schemas/task.schema.json`。`echo` 用于链路探针；`execute` 的 `program` 必须对应同一 VM
登记的 Artifact 目标，不能执行 Guest 上未登记的任意绝对路径。

```json
{
  "$schema": "../schemas/task.schema.json",
  "schema_version": 3,
  "name": "installer smoke",
  "artifacts": [
    {
      "source": "D:\\build\\Installer.exe",
      "vm": "vm_01",
      "destination": "artifacts/vm_01/Installer.exe"
    }
  ],
  "steps": [
    {
      "id": "install",
      "vm": "vm_01",
      "type": "execute",
      "program": "artifacts/vm_01/Installer.exe",
      "arguments": ["/quiet", "/norestart"],
      "run_as": "system",
      "retry_safe": false,
      "timeout_seconds": 600,
      "collect_files": ["logs/install.log"]
    }
  ]
}
```

`source` 必须是 Host 绝对文件路径。`destination` 必须位于 `artifacts/` 下。Artifact 在发布前后都会
计算 SHA-256；可额外提供 `sha256` 作为期望值。

`retry_safe` 只应为可证明幂等的步骤设为 `true`。安装、刷写和外部系统写操作通常应保持 `false`，避免
Agent 崩溃后自动重复执行不确定操作。

任务数组不是跨虚拟机的全局顺序。每台 VM 的 Agent 按 `steps` 中的出现顺序串行执行属于自己的步骤；不同
VM 的 Agent 独立领取任务，因此可以并发执行。数组顺序不能表达跨 VM 依赖、就绪屏障或完成通知。需要
Server/Client 协同时，当前版本应在任务脚本内使用有时间上限的就绪检查和清理，不应把固定睡眠当作可靠依赖。

## CMD 与 PowerShell 脚本

当前任务 schema 3 支持 `script`，脚本必须作为同一 VM 的 Artifact 发布，不能在 JSON 中内联命令。可用 engine：

| engine | 后缀 | 固定解释器 |
|---|---|---|
| `cmd` | `.bat`、`.cmd` | `cmd.exe /D /Q /C` |
| `windows_powershell` | `.ps1` | Windows PowerShell 5.1，禁用 profile 并使用 `-File` |
| `pwsh` | `.ps1` | PowerShell 7，禁用 profile 并使用 `-File` |

```json
{
  "schema_version": 3,
  "name": "configure vm_01",
  "artifacts": [{
    "source": "C:\\SatsumaTasks\\configure-vm-01.ps1",
    "vm": "vm_01",
    "destination": "artifacts/vm_01/configure-vm-01.ps1"
  }],
  "steps": [{
    "id": "configure_vm_01",
    "vm": "vm_01",
    "type": "script",
    "engine": "windows_powershell",
    "script": "artifacts/vm_01/configure-vm-01.ps1",
    "arguments": ["argument with spaces"],
    "run_as": "system",
    "timeout_seconds": 300,
    "retry_safe": false,
    "collect_files": ["results/configuration.json"]
  }]
}
```

Windows PowerShell 5.1 的非 ASCII 脚本使用 UTF-8 BOM；PowerShell 7 使用 UTF-8 无 BOM；BAT/CMD 使用
UTF-8 无 BOM + CRLF，首版正文建议保持 ASCII。解释器必须由 inventory 声明为可用；缺少 engine、Agent
协议不是 v4 或 inventory 过期时，Host 会在正式发布前失败。完整任务结构可从
`examples/windows-script-task.json` 开始修改，其中 `source` 必须替换为真实 Host 绝对路径。

## 文件日志与收集边界

临时测试版本使用 spdlog 时，优先让程序从自身 EXE 路径计算目录，并把文件日志写到 EXE 同目录。例如 Artifact
为 `artifacts/vm_01/Release.exe`，日志为 `artifacts/vm_01/release.log`，任务必须精确声明：

```json
"collect_files": ["artifacts/vm_01/release.log"]
```

Agent 的进程当前目录是本次 Guest 工作根，不是 EXE 目录；仅配置相对路径 `release.log` 不会自动写到 EXE
旁边。`collect_files` 不扫描目录、不支持 glob，也不接受工作根之外的绝对路径。推荐同时配置 console sink 和
file sink，关键级别及时 flush：stdout/stderr 由 Agent 持续保存，被测 EXE 崩溃后已刷新文件仍会收集；若
Agent、VM 或 VMCI 通道在发布结果前失效，Guest 本地文件无法保证进入 Host 证据。OutputDebugString、ETW
和 Windows Event Log 当前不会自动收集，必须由任务显式导出为工作根内文件。

测试脚本停止被测程序时应先使用程序自身的退出命令、Ctrl+C 或其他受支持的优雅退出机制，并等待日志 flush
和文件句柄关闭；超过有限宽限时间后再强制终止。`taskkill /f` 结束进程后再增加等待时间，不能恢复尚未刷新的
用户态日志缓冲。

`execute` 和 `script` 的根进程必须在 `timeout_seconds` 内退出。Agent 将根进程及其后代放入 Windows Job
Object；超时、取消、日志超限或 Service 停止会终止完整 Job。根进程退出时，如果 Job 中仍有后代，Agent
也会清理这些后代后才发布结果。因此，仅结束被测程序的某一个 PID 不代表启动它的脚本已经退出；脚本还应
确认停止操作完成并自行返回。Windows PowerShell 5.1 中需要强制清理批处理或包装进程树时，可在有限宽限
时间后使用 `taskkill.exe /PID <pid> /T /F`，并检查退出码及目标进程是否消失。

优先用被测程序现有命令行或测试配置改变日志路径。需要源码改动时，将改动限制在测试分支、独立工作树或可
审阅补丁中，不修改生产默认值，也不把 VMCI CID、端口或机器路径硬编码进正式代码。

## 运行身份

`interactive_user` 是默认身份，适合普通应用以及需要当前用户配置文件、桌面会话或 HKCU 的任务。需要安装
驱动、注册服务或修改 HKLM 等系统管理员权限时，必须显式使用 `system`。

交互执行要求 Guest 存在活动控制台用户且执行期间身份不变化。无活动 Session、用户切换或 helper 身份校验
失败都会生成失败结果，不会自动回退到 SYSTEM。

## 多 VM 编排

带 `lifecycle` 的计划必须使用 `orchestrate`，并显式给出不会重复的 `run_id`。参考
`examples/multi-vm-task.json`：

在任何 VM 操作前先执行只读预检：

```powershell
bin\SatsumaHost.exe plan validate --config config\lab.local.json --plan task.json
bin\SatsumaHost.exe orchestrate --config config\lab.local.json --plan task.json --dry-run
```

两条命令都会检查任务结构、未知 VM、Artifact 文件及大小、Artifact/步骤对应关系和生命周期基本要求，
但不会创建租约、发布运行、启停 VM 或恢复快照。正式 `orchestrate` 也会在获取写租约和改变 VM 前执行同一
静态预检。脚本引擎在线状态仍由正式运行的环境检查确认。

```powershell
bin\SatsumaHost.exe orchestrate --config config\lab.local.json --plan examples\multi-vm-task.json --timeout-seconds 900 --boot-wait-seconds 120
```

`restore_before` 在执行前恢复快照；`on_success` 和 `on_failure` 分别定义业务成功/失败后的 VM 动作。清理按
VM 声明顺序的逆序执行。`finally` 步骤无论主任务结果如何都会尝试执行。

VM 启动后默认最多等待 Agent presence、inventory 和内部 echo 共 120 秒；Agent 提前就绪会立即继续，可用
`--boot-wait-seconds 5-300` 调整。AI 生成的计划必须让成功和失败路径最终执行 `stop` 或关机状态的
`restore`，不得使用 `leave_running`。编排输出的 `final_power_states` 或异常路径 `power_off_results` 用于核对
逐台最终电源状态。

长时间编排可使用 `--output jsonl`。Host 会把每次持久生命周期迁移输出为单行 `phase_changed` 事件，并在
阶段长时间不变时每 10 秒输出 `heartbeat`；最后一行 `run_finished` 携带完整结果。默认 `json` 模式继续只在
结束时输出一个格式化 JSON。`--report-out <path>` 可将 `orchestrate` 或 `report` 的最终 JSON 原子写入文件，
避免终端折行或显示层影响机器解析。协议 JSON 时间继续使用 UTC。

schema 3 的顶层 `cleanup` 控制文件保留：Guest 使用 `delete`/`retain`，Host 运行状态使用
`retain`/`archive_then_delete`。Host 状态运行只会在归档并校验成功、Guest 清理回执成功后删除；VM 动作是
`restore` 时可直接依赖快照回退本地目录。人工介入固定保留现场，清理失败返回 `RECOVERY_FAILED` 并保留租约。

## 运行管理

```powershell
bin\SatsumaHost.exe runs list --config config\lab.local.json
bin\SatsumaHost.exe runs cancel --config config\lab.local.json --run <run-id> --reason "operator request"
bin\SatsumaHost.exe runs finalize --config config\lab.local.json --run <run-id>
bin\SatsumaHost.exe runs prune --config config\lab.local.json --keep 20
bin\SatsumaHost.exe lab status --config config\lab.local.json
```

`report` 和 `runs list` 默认先查询 Host active 状态，再查询带完整发布标记的编排证据归档；输出中的
`source` 为 `active` 或 `archive`。使用 `archive_then_delete` 删除 active 状态后，仍可使用原 `run_id`
查询报告，不需要手工遍历 archive 目录。

取消会终止正在运行的进程树并保留失败证据。`prune` 只删除保留数之外、已收到全部规范结果的运行；pending、
invalid 和人工门禁运行会保留。

同一 `lab_id` 的写操作由进程互斥和 `<archive-root>/coordination/lab-lease.json` 双重保护。普通 `run` 发布后
Host 虽已退出，租约仍为 active；报告终态并完成需要的清理后使用 `runs finalize`。自动化应优先使用
`orchestrate`，使租约覆盖启动、check、运行、归档和清理全过程。Host 崩溃后使用 `lab status` 检查；只有
同一 `run_id` 且状态可恢复时使用 `lab recover --plan ...`。状态不确定时不得删除租约；确认进程已死且外部
状态已人工核对后，才可执行 `lab unlock --force true`。

`check`、`run`、`orchestrate`、VM 启停/恢复、快照创建/删除、Agent 更新/重绑、inventory refresh、运行
取消/裁剪/终结和 Lab 恢复/解锁都属于写命令，同一 Lab 必须串行。`report`、`runs list`、`lab status`、
`discover`、`snapshot list` 和 `agent inventory` 是只读查询。即使分别指定不同 VM，也不要并发执行两个
`check`；推荐一次检查整个 Lab，或按 VM 顺序执行。写会话冲突时等待当前命令完成，不要结束未知 PID 或强行
删除租约。

## 快照恢复与宿主状态清理

基础快照是专用实验 VM 的主要恢复手段之一。Agent 长时间失联、更新或回滚无法收敛、Guest 状态无法证明、
测试污染难以精确清除时，应停止继续复用现场，保留证据后恢复用户确认的基础快照。短暂的 Tools 或 VMCI 通道
抖动仍应先执行有限等待；同一故障重复出现时不得循环重启或连续恢复快照。

VMware 快照只回退 Guest 的磁盘和可选内存。Host `transport.state_root`、`archive_root`、Host 进程和持久租约都不会
随快照回滚。人工恢复必须按以下顺序执行：

1. 保存 `lab status`、运行报告、`lifecycle.json` 和相关错误日志，确认恢复会放弃哪些 Guest 状态。
2. 确认原 Host 进程已经退出。若同一 `run_id` 可恢复，优先执行 `lab recover --plan ...`；只有进程已死、
   证据已保存且外部状态已核对时，才使用 `lab unlock --force true`。
3. 硬停止目标 VM，阻止旧 Agent 继续上传。不得在 VM 或原 Host 仍可能写入时移动协议状态。
4. 按目标 VM 和运行范围归档遗留 Host 状态，再移走已经明确放弃的更新或临时状态；不得清空整个状态根。
5. 执行 `vm restore` 恢复已确认的基础快照，再按需启动 VM。
6. 等待新的 Agent presence，并核对 `boot_id`、`session_id`、进程 ID、版本、二进制哈希和时间戳均属于恢复后
   的现场。仅看到旧 presence 文件存在不代表 Agent 已上线。
7. 执行目标 VM 的完整 `check`。只有 VMware、Guest 通道、inventory、presence 和文件往返均通过，环境才可
   重新投入任务。

Host 状态根按下表处理：

| 路径 | 恢复前处理 |
|---|---|
| `updates/<vm-id>/` | 归档已放弃的更新清单、候选和结果；确认更新事务不会继续后再移走 |
| `agents/<hardware-id>.json`、inventory 和请求文件 | 归档旧规范状态，恢复后必须等待新 session；不要把旧时间戳当作在线 |
| `agents/.../sessions/` | 作为诊断证据保留，可按独立保留策略清理，不作为当前在线状态 |
| `runs/<run-id>/`、claim 和结果 | 不手工清空；按 `lab recover`、`runs finalize` 和任务 cleanup 策略处理 |
| `archive_root/coordination` | 不随 VM 恢复删除；先解析租约和原 Host 状态 |
| 安装材料和其他 VM 的目录 | 保留，不得因单台 VM 恢复而删除 |

Host 没有需要随 VM 重启的常驻服务。这里的“重启 Host”是指在原 Host 进程确认退出、租约和持久状态处理完成
后启动新的 CLI 进程，不是重启宿主操作系统，也不是在旧 Host 仍运行时并发启动第二个 Host。

## Agent 更新与身份迁移

更新会把候选二进制发布到 Host 状态根，Agent 经 VMCI 下载并校验大小和 SHA-256 后停止 Service、切换文件、重启并验证
新 presence。失败会尝试恢复旧二进制和配置。

同一语义版本可能包含不同修复构建。`check`、`discover` 和 Agent presence 会显示 Build Number、Run Attempt、
Git Commit 与 `binary_sha256`。需要锁定精确构建时，在对应 VM 配置中设置可选的 `agent_sha256`；Host 在
正式检查和任务发布前读取 presence，实际 Agent 哈希不匹配时立即拒绝继续。

更新成功只改变当前 Guest 磁盘，不会重写已有 VMware 快照；恢复配置中的 base 可能把 Agent 回退到旧构建。
成功输出会包含 `AGENT_UPDATE_NOT_IN_BASE_SNAPSHOT` 警告。更新后的推荐流程是：核对 presence 中的版本、
Build 信息和 SHA-256，正常关闭 Guest，创建并批准新的冷快照，更新 `restore_before` 或 base 配置，再运行
`check`。在新快照确认前，不要执行会恢复旧 base 的生命周期任务。

```powershell
$targetVersion = (& bin\SatsumaVM.exe --version).Trim()
bin\SatsumaHost.exe agent update --config config\lab.local.json --vm vm_01 --binary bin\SatsumaVM.exe --version $targetVersion --timeout-seconds 300
```

新安装或硬件 UUID 变化后的 Agent 会以 `status=unbound` 上线。确认对应关系后绑定硬件身份：

```powershell
bin\SatsumaHost.exe discover --config config\lab.local.json
bin\SatsumaHost.exe agent rebind --config config\lab.local.json --vm vm_01 --hardware-id <uuid>
```

Agent 在安装根目录保存 `hardware-id-cache.json`。检测到 UUID 变化时会发布
`agents/<old-hardware-id>.migrated.json`，presence 同时带上旧硬件和旧 VM 标识，供 Host 诊断。

某些通过复制磁盘、NVRAM 或带内存状态快照生成的 VM 会保留相同 SMBIOS UUID。`discover` 此时返回
`status=identity_conflict` 并列出冲突的 VM 标识，Host 拒绝绑定。应先在 VMware 中为克隆生成新的 UUID，确认
Guest 内 `Win32_ComputerSystemProduct.UUID` 已变化后再重试；不要用自定义标签或随机文件掩盖硬件冲突。

旧版带 `vm_id` 的 Agent 仍可在更新二进制时迁移到另一个 VM 标识：

```powershell
$targetVersion = (& bin\SatsumaVM.exe --version).Trim()
bin\SatsumaHost.exe agent rebind --config config\lab.local.json --vm vm_01 --next-vm vm_01-2 --binary bin\SatsumaVM.exe --version $targetVersion --timeout-seconds 300
```

目标 ID 已存在 presence 时迁移会被拒绝，防止两台 VM 共用身份。

## 退出码

| 命令结果 | 退出码 |
|---|---:|
| 成功或未等待的 pending 报告 | 0 |
| 业务失败或普通运行错误 | 1 |
| 命令行参数错误 | 2 |
| 检查 degraded 或等待超时 | 3 |
| 生命周期或清理恢复失败 | 4 |
| 需要人工介入 | 5 |

自动化应同时检查退出码和 JSON 顶层 `status`。未使用 `--wait-seconds` 的 `report` 返回 `pending` 时退出码为
0，表示查询本身成功，并不表示任务已完成。

## 排障

| 错误或状态 | 主因与处理 | 自动重试 |
|---|---|---|
| `STEP_TIMEOUT` 或 `timed_out` | 先查超时、完整进程树和剩余业务状态；文件缺失是次生诊断 | 仅 `retry_safe=true` |
| `Declared result file does not exist` | 进程正常结束时检查脚本落盘路径；若同时超时，先处理超时 | 修复计划后新建 run |
| `Another SatsumaHost write session...` | 按错误中的 Command、PID、Lease 等待占用命令结束，写命令串行执行 | 等待后可重试 |
| `Snapshot base name must not use the AI snapshot prefix` | base 改回用户快照；AI 快照只能由任务显式引用 | 修正配置后可重试 |
| `manual_intervention_required` | 保留 lease、运行证据和 VM 状态，人工确认外部副作用 | 禁止自动重试 |
| `Unknown run_id` | 同时检查 active 和带完成标记的 archive；新版 CLI 已自动查询两者 | 不适用 |
| `Agent binary SHA-256 mismatch` | 恢复到了旧快照或运行了错误构建；停止业务步骤并核对 Build/Commit/哈希 | 修复快照后重试 |

人工门禁和恢复失败时至少保留 `lab status`、`lifecycle.json`、运行报告、claim、stdout/stderr、Agent presence
及 VM 最终电源状态。不得为了重试删除未知租约、伪造结果或清空整个 Host 状态根。

- `check` 失败：先核对 `vmrun`、VMX、网关进程、VMCI CID 和端口。
- Agent 不上线：在 Guest 检查 `Get-Service SatsumaVM`，再前台运行 `--validate-config`。
- 冷快照恢复后 Agent 不上线：确认快照制作于 Agent 安装和验收之后，并检查 Service `StartType` 为
  `Automatic`；旧快照需要重新安装并重新制作。
- `inventory identity mismatch`：等待绑定后的 Agent 下一轮轮询；新版会在同一进程内重建 inventory，无需
  重启 Service 或 VM。
- 死亡 Host 留下 `run_id` 为空的失败租约：先确认原进程已退出；新版 `check` 和 inventory refresh 的普通
  失败会自动释放，异常断电等无法完成终态写入时仍按 `lab status` 和 `lab unlock --force true` 门禁处理。
- 某个运行为 `invalid`：检查该目录的 `task.json` 和 `state/<vm>-agent-error.json`；其他运行仍会继续。
- `manual_intervention_required`：先核对被测程序和外部系统状态，不要直接删除 claim 或伪造结果。
- 日志超限：步骤会失败并终止进程树；减少输出或改为写入有明确容量约束的收集文件。
- 磁盘增长：定期执行 `runs prune`，并为 Host 归档目录设置独立的组织级保留策略。
