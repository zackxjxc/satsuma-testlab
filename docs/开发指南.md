# 开发指南

## 工具链

- Windows 10/11 x64。
- Visual Studio 2022，安装 Desktop development with C++ 和 Windows 10/11 SDK。
- CMake 3.25 或更高版本。
- Git；首次配置且本机没有包时需要访问 GitHub 获取固定版本的 `nlohmann/json`。
- PowerShell 7 仅用于真实 VMware 故障恢复脚本测试；普通构建仍兼容系统 `powershell.exe`。

项目使用 C++20 和静态 MSVC Runtime。当前不支持非 Windows 平台，配置阶段会直接拒绝。

## 构建与测试

```powershell
cmake --preset windows-default
cmake --build --preset windows-debug --parallel
ctest --preset windows-debug
cmake --build --preset windows-release --parallel
ctest --preset windows-release
```

Debug 与 Release 共用 `build/windows-default` 多配置目录。默认测试不操作真实 VMware，只使用临时本地状态
目录、Fake `vmrun`、inproc VMCI 通道和专用测试进程。

测试层次：

- 核心：配置、路径、JSON 原子写入、SHA-256、任务、协议和 claim 模型。
- VM：claim 续租、Job Object、交互用户、Service、自更新和故障隔离。
- Host：运行发布、报告、取消、保留、更新发布和 VMware Provider。
- 集成：单 VM VMCI 流、多 VM 生命周期、单文件安装安全检查和示例应用。
- Schema：本地 CTest 使用固定版本的 jsoncons 执行 Draft 2020-12 示例校验，并检查全部 Schema 文档可解析；
  CI 额外执行 metaschema 校验。

修改 VMCI 协议、Controller、Agent 或 Service 时应运行完整 Debug/Release 测试。只改文档时至少运行 Schema
检查和 `git diff --check`。

安装升级、普通用户权限、长路径和故障恢复的具体矩阵及真实 Guest 开发夹具，见
[验收与测试边界](验收与测试边界.md)。测试工具使用独立夹具验收，不依赖使用者业务项目；UAC 界面测试须与
SYSTEM 下的安装逻辑测试分别记录。

## 发行目录与打包

生成展开版发行目录和 ZIP：

```powershell
cmake --build --preset windows-release --target SatsumaPackage
```

产物位于根目录 `output/SatsumaTestLab-<version>-windows-x64/` 和同名 ZIP，不会向系统安装文件。该目标使用
PowerShell 调用 .NET ZIP API 写入 Unicode 文件名并保留发行根目录，避免在中文 Windows 上把中文文件名写成
无编码声明的本地代码页字节。

发行物只包含 Host/VM 生产二进制、待填写配置模板、任务示例、Schema、公开文档和与二进制版本
配套的 AI Skill。`packaging/README.release.md.in` 和 `packaging/AI-START-HERE.md.in` 由 CMake 使用
`PROJECT_VERSION` 生成发行包根目录的 `README.md` 与 `AI-START-HERE.md`；GitHub 首页继续使用源码根目录
的 `README.md`。测试夹具、Fake `vmrun`、真实故障注入脚本和已填写的本机配置不进入发布包。
打包脚本读取两个最终 EXE 的 `--version --json`，拒绝版本或构建身份不一致的 Host/Guest。包根生成
`BUILD-INFO.md` 和 `release-manifest.json`，后者记录自身以外所有文件的相对路径、大小与 SHA-256。
Guest 子目录仍只包含 `SatsumaVM.exe`；ZIP 的 SHA-256 另写在包外。

## 代码结构

```text
include/satsuma/core/   公共核心模型与 VMCI 协议
src/core/               配置、任务、JSON、路径、哈希、claim、更新模型
src/host/               Controller、诊断、生命周期编排和 CLI
src/vm/                 Agent、Service、进程执行、claim 事务和自更新
src/vmware/             vmrun Provider
schemas/                JSON Schema Draft 2020-12
config/                 Host 与 Agent 发行配置模板
packaging/              发行包入口文档模板
skills/satsuma-testlab/ 与当前产品版本配套的 Agent Skill
scripts/                构建和发行辅助脚本
tests/                  单元、集成与显式真实 VMware 验收
```

`SatsumaCore` 不依赖 Host/VM 具体实现；`SatsumaHostLib` 和 `SatsumaVmLib` 分别承载生产逻辑。测试专用 VM
库只把三个测试宏集中编译一次，并与生产 VM 库共享源文件清单，避免构建目标逐渐漂移。Host CLI 将参数路由
与命令处理分离；Orchestrator 和 Agent 分别按生命周期阶段与执行/发布阶段组织。

## 变更规则

- 现有文本保持 UTF-8 和 LF；`scripts/package-release.ps1` 按 `.editorconfig` 保持 UTF-8 BOM。Guest 安装入口在 `src/vm/install.cpp`，发行介质只有 EXE。
- 不批量格式化无关文件。MSVC 使用 `/W4 /permissive- /utf-8`，新增警告应在提交前处理。
- 用户输入 JSON 应拒绝未知字段，避免拼写错误静默回退。
- Host/Guest 本地状态写入使用项目的原子 JSON/目录发布函数，不直接覆盖规范协议文件。
- 新增路径必须通过 `resolve_under_root` 或等价验证，不能信任任务中的相对路径。
- 新增长任务必须接入停止令牌和 Job Object，不能只终止父进程。
- 修改 VMCI 协议时同步更新 C++ 验证、Schema、协议文档和端到端测试。
- 修改 CLI、Schema、首次配置或恢复语义时，同步更新对应的 Skill reference，不在 `docs/AI操作契约.md` 复制
  第二套 AI 操作流程。

## 文档与版本

产品版本只以顶层 `project(SatsumaTestLab VERSION ...)` 为权威值。Host/Agent 的 `--version` 输出、Windows
可执行文件属性和发行入口文档均由 CMake 取得该值；`skills/satsuma-testlab/SKILL.md` 的
`metadata.satsuma-version` 需要显式更新，CMake 配置阶段会拒绝不匹配的版本。CTest 会读取最终 EXE 的
Windows 版本资源，防止发布文件漏写或写入错误版本。

`SatsumaBuildIdentity` 在每次构建前检查真实 Git HEAD 和工作区，统一生成 C++ 与 Windows 资源使用的身份。
未提交改动标记为 `-dirty`；本地构建号为 `local.<源码指纹>`，包含未跟踪源码的内容变化。CI 可提供构建号和
尝试号；显式指定的提交号必须匹配真实 HEAD。缺少可核实 Git 身份时不得打包成已知提交发行物。
构建号不参与双击升级的版本高低比较，精确文件内容仍以 SHA-256 为准。

根目录 README 和 `docs/` 中的长期文档不写死“本文适用于某个当前版本”。`master` 描述正在开发的版本，稳定
文档由 Git Tag 和 GitHub Release 固定。命令示例需要版本参数时，从目标二进制的 `--version` 输出取得，不在
教程中长期保存具体版本号。

## 真实 VMware 测试

真实目标默认不存在，避免普通 `ctest` 误操作用户 VM。只能对专用实验 VM 启用，并提供明确确认字符串与
真实配置：

```powershell
cmake -S . -B build\real -DSATSUMA_ENABLE_REAL_VMWARE_SMOKE=ON -DSATSUMA_REAL_LAB_CONFIG=D:\lab.local.json -DSATSUMA_REAL_VM_ID=vm_01 -DSATSUMA_REAL_SNAPSHOT=clean -DSATSUMA_REAL_VMWARE_CONFIRM=I_UNDERSTAND
cmake --build build\real --config Release --target SatsumaRealVmwareSmoke
```

Host/Agent 强制终止测试由 `SATSUMA_ENABLE_REAL_VMWARE_CRASH_RECOVERY` 控制。确认字符串、超时和目标必须按
CMake Cache 描述显式提供。VMCI 断线恢复应在专用实验 VM 中通过停止/重启 Host 网关验证；不要对包含未保存
工作或唯一证据的 VM 运行这些目标。

崩溃驱动会先用实际 Host CLI 校验生成的计划，再等待生命周期和 claim。内部场景之间保留 VM 运行，以检查
服务恢复和下一场景；外层测试必须负责最终关机、停止测试 gateway，并按授权恢复测试前快照。
`AgentUnsafe` 只针对专用夹具：核对没有第二次执行、没有伪造规范结果并保存人工门禁证据后，才释放本轮
测试租约。这不是使用者任务的自动解锁流程。普通运行仍遵守[执行、结果与恢复](../skills/satsuma-testlab/references/operations.md)。
非安全步骤进入人工门禁时，工具会安全关闭 VM。因此 `AgentUnsafe`/`All` 的最终检查应为
`expected_stopped`，其余场景应为 `ready`；不能要求已经关机的 VM 在线，也不能忽略其他环境检查错误。

## CI 与发布检查

Guest 双击入口在 `src/vm/install.cpp`，与服务维护 CLI、更新辅助进程共用机器级安装锁。
首次安装使用受保护的 ProgramData 目录，校验 EXE 版本资源、PE 校验和及复制前后的 SHA-256；
这些检查用于发现错误文件或损坏，不代替发行者数字签名。已有安装先验证命令、布局和权限，再显示状态。
双击按三段或四段数字版本比较，禁止降级；同版本比较整个 EXE 的 SHA-256，不同则更新。
本机更新先校验暂存 EXE、备份配置，再停服替换；验证 SCM 运行状态、新服务 PID、进程映像及 EXE 哈希后提交，
失败恢复旧 EXE、配置和服务。配置只更新 agent_version，保留其他字段；不依赖 Host 在线。
install-pending.json 记录事务阶段，异常中断保留现场供人工恢复。现有 Host 更新事务仍可使用。
旧任务迁移只有在服务启动成功后才删除任务，
失败时恢复旧任务。未知服务、任务、目录以及中断现场不会被自动接管。
历史脚本只保护 agent/work：允许安装根和 mirror 存在宽松 ACL，但其所有者仍须为 SYSTEM/Administrators，
agent 全树与 work 根仍须通过严格检查。完整确认服务/任务归属后才修复，锁定目录后调用
SetFileSecurity，仅修改目录本身，不传播到已有子对象。install-acl-repair.json 标识中断现场。
UAC 成功启动管理员进程后父进程立即返回；取消 UAC 时仍在原窗口报告失败并等待 Enter。

`SatsumaVmInstallTests` 覆盖数字版本比较、损坏介质、错误 EXE、目录权限与并发互斥，不操作本机服务。
`SatsumaVmInstallRollbackProbe --simulate-local-update-failure <介质路径>` 在替换 EXE 后注入失败，供隔离 Guest 验证更新回滚。
`SatsumaVmInstallRollbackProbe --simulate-task-delete-failure` 仅供已明确授权的隔离 Guest 使用：
它在旧任务迁移过程中模拟删除任务失败，用于验证真实 SCM 与任务调度器的恢复；不注册为普通 CTest，
也不进入发行包。真实 Guest 验收应覆盖无参数首次安装、重复运行、未知服务/任务拒绝、迁移及回滚、
无 Host 时启动和重启后自动重连。UAC 确认、取消及窗口等待行为另做交互验收。

证据暂存使用扁平的 `<storage_root>/staging/<job-id>`，Host Artifact 使用 `.artifacts/<清单序号>.bin`。
工作目录共享、交互日志 ACL、Host 规范结果路径和旧运行兼容均保留，详见[短路径存储设计](短路径存储设计.md)。
缩短内部目录后仍须支持合法长路径：文件生成、复制、哈希、流式打开、上传、下载及删除统一使用扩展 Win32
路径边界，不修改 Guest 的全局长路径注册表开关，也不将扩展前缀写入配置或 VMCI 协议。

相关回归包括：跨 VM 同路径同/不同内容与同 VM 重复拒绝、旧 Artifact 布局、超过 MAX_PATH 的实际文件读写、
尝试目录隔离和归属记录、上传失败摘要与本地证据保留、失权后的 fencing、Agent 错误提前报告，以及构建身份和
发行清单一致性。`SatsumaVmciFileTests`、`SatsumaVersionInfoTests`、`SatsumaBuildIdentityTest`、
`SatsumaPackageReleaseTest` 与 Host/Agent 测试共同覆盖这些边界；每次交付的通过情况以该次测试日志为准。

Windows CI 对每次 push/PR 执行：Schema 校验、Debug 构建测试、Release 构建测试和 UTF-8 ZIP 打包。准备发布时
还应在本机完成：

1. `SatsumaHost --help`、`SatsumaVM --help` 和 `--version` smoke。
2. 检查 `output` 展开目录和 ZIP 中包含发行 README、`AI-START-HERE.md` 和完整 Skill，同时不存在测试工具、
   机器绝对路径或已填写的本机配置。
3. 对专用 VMware 环境执行一次最小 `check`、`run`、`report`。
4. 检查 `CHANGELOG.md`、`THIRD_PARTY_NOTICES.md`、CMake/二进制/Skill/发行包版本和许可证状态。
5. 运行 `git diff --check`，确认没有编码、换行或无关整文件变化。
