## 1. 当前整体的代码结构思路

### 1.1 项目定位和责任边界

Satsuma 是可信本机 Host 与隔离 Windows VM 之间的小任务下发器。它负责：

- 控制 VMware VM 的启动、停止和快照恢复。
- 将 Host 构建产物物化为带哈希的任务 Artifact。
- 让 VM Agent 在 Guest 本地目录执行程序。
- 管理进程树、超时、stdout、stderr 和结果文件。
- 保存机器可读执行证据，并向上层 AI 返回平台状态。

Satsuma 不判断被测程序的业务逻辑是否正确。业务断言、测试参数、结果解释和目标项目修改由调用它的
AI 或程序员负责。

Host 不运行业务 Artifact，也不修改 Host 服务、驱动、防火墙、网络或注册表；它只运行 Satsuma 自身
程序、构建和测试，写入专用数据目录，并控制配置中的授权 VM。

### 1.2 双端程序和运行通道

项目构建两个运行程序，共享一个静态核心库：

```text
SatsumaCore（静态库）
  ├── SatsumaHost.exe（宿主机）
  └── SatsumaVM.exe（每台测试 VM）
```

生产运行使用共享文件事实源与 `vmrun` 带外控制，RPC 仅保留为独立诊断入口：

```text
调用方 AI / 程序员
        |
        v
SatsumaHost.exe
  ├── VMware Shared Folder：任务、Artifact、状态、日志和结果
  └── vmrun.exe：VM 电源、快照和 Guest 网络之外的带外控制
        |
        v
SatsumaVM.exe
  ├── 校验并领取任务
  ├── 按声明身份复制 Artifact 到 SYSTEM 或交互用户本地目录
  ├── 使用 Windows Job Object 执行、取消和超时终止完整进程树
  └── 原子发布 execution.json、日志和收集文件

可选诊断：SatsumaHost serve <--- coro_rpc ---> SatsumaVM --rpc-once
```

共享目录是唯一任务事实来源；`--watch` 和 Windows Service 不启动、不调用也不等待 RPC。`vmrun` 用于
VM 生命周期和最终带外恢复。现有 RPC DTO、Server 与 `--rpc-once` 已冻结，仅保留为本机诊断入口。

### 1.4 当前运行目录模型

Host 为每次任务创建唯一 `run_id`，先在点号前缀暂存目录中完成写入，再整体发布为 Agent 可见目录：

```text
shared_folder.host_root/runs/<run_id>/
├── task.json
├── artifacts/
│   └── <vm-id>/...
├── state/
│   ├── <vm-id>/<step-id>.claim.json
│   ├── <vm-id>/<step-id>.claim-renewal-<job-id>-<sequence>.json
│   └── <vm-id>-agent.json
└── results/
    └── <vm-id>/<step-id>/
        ├── execution.json
        ├── stdout.log
        ├── stderr.log
        └── files/...
```

`claim.json` 通过独占创建避免同一步骤被多个 Agent 会话重复领取；后台续租发布不可变、连续编号的
sidecar，读取时校验 owner、序号以及时间和截止时间单调递增。Artifact 先在共享目录校验哈希；
`system` 步骤复制到 `agent.json` 的 `local_work_root/<run_id>/`，`interactive_user` 步骤复制到活动用户的
`%LOCALAPPDATA%\SatsumaTestLab\<lab-id>\runs\<run-id>`，都不直接从 UNC 路径运行程序。

### 1.5 当前命令入口

Host 已实现：

```text
SatsumaHost check
SatsumaHost serve
SatsumaHost vm start|stop|restore
SatsumaHost snapshot list|create-ai|delete-ai
SatsumaHost agent update
SatsumaHost run
SatsumaHost orchestrate
SatsumaHost report
```

VM Agent 已实现：

```text
SatsumaVM --once
SatsumaVM --rpc-once
SatsumaVM --validate-config
SatsumaVM --watch
SatsumaVM --service
SatsumaVM --install-service
SatsumaVM --remove-service
SatsumaVM --install-autostart
SatsumaVM --apply-update
```

`--install-autostart` 只为旧环境回滚保留；新安装与升级由 `install-agent.ps1` 调用 Service 入口。

任务步骤当前支持 `echo` 和 `execute`；计划中的 `execute.run_as` 可选择 `system` 或
`interactive_user`，省略时为 `system`。Host 发布文件协议 v2 清单时会显式物化 execute 身份；
生命周期策略支持一台或多台 VM 的 `restore_before`、成功/失败动作和 `finally`。多 VM 按生命周期声明
顺序恢复、启动并逐台检测 Agent，全部 Ready 后才发布主任务，最终按逆序执行 cleanup。

### 2.3 Host 文件任务闭环

- `run` 能读取任务文件、校验 VM 引用并生成唯一或调用方指定的 `run_id`。
- Host 能复制 Artifact、计算实际 SHA-256，并验证可选的预填哈希。
- Artifact 目标被限制在 `artifacts/` 子目录。
- 运行目录在隐藏暂存阶段准备完成后一次性发布，Agent 不会读取半成品 manifest。
- `report` 能统计预期、已报告、成功和失败步骤，并返回执行明细。
- Controller 同时支持从 JSON 文件和内存任务计划物化运行，供主动检测复用。

### 2.4 VM Agent 执行闭环

- Agent 能扫描共享目录并只处理匹配 `lab_id`、protocol 和 `vm_id` 的步骤。
- Agent 能独占创建 claim，避免正常并发场景下的重复领取。
- Agent 使用 120 秒固定租约，每 30 秒发布不可变序号续租记录；连续失败会在安全截止前取消进程树。
- 显式 `retry_safe` 的过期 claim 可归档旧 owner 并以递增 attempt 接管，旧 Job 结果不能覆盖新 owner 的
  规范证据；`boot_id` 用于取证，不是接管前置条件。
- Agent 能校验 Artifact 哈希，复制到 Guest 本地目录后执行。
- `echo` 步骤能生成无害 stdout 结果。
- `execute` 步骤支持参数数组、本地工作目录和有限超时。
- Windows Job Object 能在超时时终止被测进程树。
- stdout/stderr 使用 `.partial` 文件写入，完成后原子发布最终日志。
- Agent 能收集任务声明的结果文件并记录 SHA-256。
- SYSTEM 步骤保持原有本地目录和 ProcessRunner 路径；生产承载为 LocalSystem Service。
- `interactive_user` 使用活动控制台用户 Token 和 `%LOCALAPPDATA%` 工作目录；无 Session 时稳定失败，
  不回落 SYSTEM，且不阻塞后续步骤。
- 交互 helper 在用户 Session 内启动目标，helper、目标和子进程共用 Job Object、超时和 stop/cancel。
- 启动前及恢复挂起 helper 前核对 Session、SID 和 `AuthenticationId`，避免注销重登后使用旧 Token。
- `execution.json` 记录请求身份、可选交互 Session、状态、退出码、超时、耗时、日志、错误和收集文件。
- `--watch` 只扫描共享目录，不启动 RPC 客户端，也不等待 Host Server。
- Agent、Artifact 复制、步骤循环和 ProcessRunner 支持 `std::stop_token` 取消。
- Service STOP/SHUTDOWN 可取消运行中的 Job Object；结果固定写入失败状态和 `Agent stop requested`。

### 2.5 RPC 诊断入口

- 已定义版本化的 Agent 注册、心跳、任务轮询和 Job 状态 DTO。
- Host 能校验 `lab_id`、`vm_id`、Agent 版本、`session_id` 和 `boot_id`。
- 诊断客户端能注册、心跳、接收任务引用并上报运行/完成状态。
- Host `serve` 能在 `lab.json` 指定的地址启动 `coro_rpc` Server。
- 已有本机回环测试覆盖 RPC 注册、状态、任务发现和结果上报。
- `--rpc-once` 是唯一保留的 VM 侧 RPC 入口；`--watch` 与 `--service` 完全不使用该通道。
- 该实现冻结为非生产诊断能力，不作为文件任务成功、取消或恢复的判定依据。

### 2.6 VMware 带外控制和快照保护

- `vmrun list` 运行状态查询。
- VM 无界面启动。
- VM 软关闭和硬关闭。
- 恢复指定快照。
- 查询快照列表、创建快照和删除快照。
- `vmrun` 通过 `CreateProcessW` 接收结构化参数，不使用拼接的 `cmd /c`。
- `vmrun` 进程受超时和 Job Object 约束。
- 用户基础快照与 AI 派生快照有不同所有权。
- AI 快照使用配置前缀、时间戳和数量配额。
- Host 拒绝删除用户基础快照或非 AI 所有权快照。
- AI 快照创建/删除状态会写入 `archive_root/snapshots/<vm-id>/` 元数据。
- 快照创建或删除命令返回错误后会重新列举快照；目标已出现或消失时按实际状态完成对账，并在元数据中
  保留原始操作错误和对账时间，避免 `vmrun` 超时却已实际成功时误报失败。
- 已提供默认关闭的真实 VMware 生命周期 smoke 目标，要求显式确认字符串后才允许运行。

### 2.7 Guest 无人值守启动

- `SatsumaVM --install-service` 创建或更新 `SatsumaVM` Service，并返回实际 Service PID。
- Service 使用 LocalSystem、延迟自动启动，以及 5/15/60 秒失败重启和 non-crash failure actions。
- SCM 命令固定为本机安装中的
  `"<install-root>\bin\SatsumaVM.exe" --config <install-root>\agent.json --service`。
- STOP/SHUTDOWN 先请求取消；Agent 清理和退出码确定后，`SERVICE_STOPPED` 恰好最后上报一次。
- 安装和更新只写入当前所需配置，不保存或恢复完整 SCM 快照、DACL 或 owner。
- 停止逻辑会处理 `START_PENDING`/`STOP_PENDING` 并有限等待；安装等待 `RUNNING` 和有效 PID。
- `--remove-service` 有限等待停止、关闭删除句柄并等待 SCM 对象真正消失；Service 不存在时幂等返回。
- `SatsumaVM --validate-config` 只做配置解析预检，不会创建任务或访问 VMware。
- `--once`、`--watch` 和 `--rpc-once` 不修改 SCM 或系统启动配置。
- `install-agent.ps1` 能自动请求 UAC、串行安装、复制并校验固定 `.new` 文件、停止 Service、迁移旧任务、
  切换文件并启动 Service；失败时只做一次简单文件恢复，复杂故障使用 Guest 快照。
- 安装成功后删除 `.bak`、`.new` 和配置暂存文件，不永久保留旧版本。
- `--watch` 与 Service 容忍 Shared Folder 暂时不可用，避免 VMware Tools 启动竞态导致进程退出。
- Agent 会在共享目录发布带 PID 的 `agents/<vm-id>.json` 就绪状态，供安装脚本和诊断核对实际进程。
- MSVC 构建使用静态 Runtime，Guest 不需要安装与构建机完全一致的 Visual C++ Redistributable。
- 已在真实 Guest 验证 LocalSystem、延迟自动启动、固定 SCM 命令、安装后启动及快照恢复后无人登录上线。

### 2.8 Agent 自更新

- Host 使用独立 `agent update` 通道，在隐藏目录完成候选复制、size/SHA-256 校验和原子发布。
- Agent 把候选复制为本机 `SatsumaVM.new.exe`，再由候选以独立 `--apply-update` 模式执行切换。
- helper 有限停止/启动 Service，并通过新 PID、版本和 update ID presence 确认新 Agent。
- 更新成功会把旧 v1 配置升级到文件协议 v2；启动失败会恢复旧 EXE、旧配置和旧 presence。
- 删除 `.bak.exe` 是不可逆提交点；提交后由新 Agent 重试剩余清理，不再回滚已运行的新版本。
- 成功结果发布前必须删除 `.bak.exe`、`.new.exe`、配置备份、manifest 和 state；共享结果写入不会
  在 Host 清理后重新创建父目录。
- 已通过真实 Win32 文件切换、运行中候选自重命名、注入式 SCM/presence 状态机和并发恢复测试；动态
  Runtime 候选和静态 Runtime 候选均已完成真实 SCM/Guest 自更新、presence 和暂存清理验收。

### 2.9 AI 主动检测模式

`SatsumaHost check` 已实现以下检查：

- Host 共享目录是否存在、报告容量并支持原子写入。
- Host 归档目录是否存在、报告容量并支持原子写入。
- `vmrun.exe` 是否存在。
- `vmrun list` 是否能执行。
- 目标 VMX 是否存在。
- 快照列表是否包含配置的用户基础快照。
- VMware Tools 是否对目标 VM 报告 `running`。
- 自动发布唯一 echo 任务并等待目标 Agent 返回。
- 校验 Agent 结果状态、退出码、超时标记和 stdout 内容。

Shared Folder 失败时不再尝试发布任务；报告保留环境检查、`run_id=null` 和每台 Agent 的 `skipped`
原因。结果读取遇到瞬时文件错误时会有限重试，截止时间后保留最后一次错误。任务发布 staging 的初始化
也位于清理边界内，早期空间或目录错误不会有意保留 `.preparing-*`。

报告区分：

- `ready` / 退出码 0：环境与 Agent 探针均正常。
- `degraded` / 退出码 3：Agent 探针正常，但某项 VMware/Host 环境检查失败。
- `failed` / 退出码 1：Shared Folder 阻断探针、Agent 超时、结果失败或内容不匹配。

## 3. 已冻结的项目范围

项目定位已经收敛为可信本机环境中的 Windows VM 小任务下发器。Host 负责发布任务、控制已授权 VM、
等待结果和收集证据；被测程序只在 Guest 内执行，单个任务通常在数秒到数分钟内结束。

### 3.1 当前支持范围

- 一台或多台 Windows VMware Guest，使用 Shared Folder 传递任务和结果。
- `echo` 与前台 `execute` 小任务，以及 SYSTEM 和活动交互用户两种身份。
- 有限超时、完整进程树终止、stdout/stderr 和声明文件收集。
- Agent Windows Service、自更新、主动检测和显式 VM 启停或快照恢复。
- 可选生命周期编排；现有能力保持稳定，但不再扩展为通用工作流引擎。

### 3.2 明确不再开发的能力

- 磁盘满、VMware Tools 服务失效、断网、危险网络和 Guest 卡死的专项恢复。
- 注销重登竞态、恶意输入、长时间稳定性、大 Artifact 和压力测试。
- 逐 VM 断点恢复、计划级重试退避、失联 Agent 智能回收和不确定清理自动恢复。
- 步骤依赖图、后台服务、`wait-ready`、远程 `stop-job` 和并行度调度。
- 额外 `file push`、单步 `exec`、归档索引、自动清理、配额和历史统计。
- RPC 认证加密、身份凭据、密钥轮换、签名安装包、版本清单和发布渠道。
- 其他 Host、Guest 或虚拟化平台。

以上项目不是遗留缺陷，而是与当前目标无关的非目标。已有实现不删除，也不继续扩大。

### 3.3 未知平台错误的处理边界

- 已知任务非零退出保持普通任务失败，任务超时保持超时，不归入未知错误。
- 配置、路径、Artifact 和任务清单校验失败时直接停止，不重置 VM。
- 其他不在支持范围内的环境问题由使用者 AI 视为未知平台错误，并保留原始错误和现有证据。
- AI 可以选择硬重启或恢复配置中的快照，再使用新 `run_id` 重试一次。
- 重试后仍失败，或 VM 重启/恢复本身失败时，必须停止并等待用户手工排查。

Satsuma 不为未知平台错误新增自动推断或无限恢复循环。

## 4. 使用前只需完成的准备

完整步骤见 [SatsumaReadme.md](SatsumaReadme.md)。当前 Client/Gateway 实验室已经完成这些准备；新增 VM
时才需要重复执行。

### 4.1 Host 和 VMware

1. 安装 VMware Workstation，确认 `vmrun.exe`、专用共享目录、归档目录和 VMX 路径。
2. 使用普通 NAT/DHCP；项目不要求修改 Host 防火墙、路由、DNS、服务、驱动或注册表。
3. 只共享专用任务目录，不共享源码、个人目录或凭据。
4. 为可丢弃测试 VM 安装 VMware Tools，并保留一个用户维护的只读基础快照。
5. 把真实值写入已被 Git 忽略的 `lab.local.json`。

### 4.2 每台 Guest

1. 使用唯一 `vm_id` 创建 `agent.json`。
2. 验证 Guest 能读写 `\\vmware-host\Shared Folders\<share-name>`。
3. 执行一次 `scripts/install-agent.ps1` 并确认 UAC，安装 LocalSystem Windows Service。
4. 使用 `SatsumaHost check --config <配置文件>` 验证文件任务通道；通过后不需要保留人工终端。

### 4.3 每个测试任务

调用方只需提供目标程序绝对路径、参数、有限超时、需要收集的文件和业务通过条件。单步骤通常不超过
300 秒；程序只在 Guest 内执行。会修改 Host、外部网络或配置范围之外 VM 的任务不属于本项目范围。

1. 用户文档、AI 契约和示例已统一项目定位、支持边界及未知平台错误流程。
2. Debug/Release 自动化回归已覆盖当前冻结功能；最终结果见 2.11 节。
3. Client/Gateway 已完成最终 `check`、短任务、日志与结果收集验收。
4. 已授权 VM 已验证在重启或恢复现有快照后重新返回 `ready`。
5. README 和使用指南已提供从配置、检测、下发、等待到读取证据的最简操作路径。

项目不再沿旧路线图增加生产化、极端故障或复杂编排能力。进入维护模式后，只处理支持范围内可复现的
Bug，以及不扩大系统边界的低成本文档修正。

## 6. 项目完成结果

Satsuma 已同时满足以下条件，按当前范围视为完成：

- Debug 和 Release 自动化测试全部通过。
- Client 与 Gateway 的真实文件通道均返回 `ready`。
- `echo` 和数分钟内的前台 `execute` 能返回退出码、stdout、stderr 和声明收集文件。
- 超时任务会终止 Guest 内完整进程树，不在 Host 执行业务 Artifact。
- Host 不修改系统服务、驱动、防火墙、网络或注册表，只写专用数据目录并控制配置中的授权 VM。
- 未知平台错误遵循“保留证据、恢复一次、使用新 `run_id` 重试、仍失败即停止”的边界。
- 文档不再把明确取消的生产化、极端故障和复杂编排能力列为未完成工作。

基础快照删除、配置外 VM 和任何 Host 系统修改始终不在授权范围内。
