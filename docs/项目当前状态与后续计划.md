## 1. 当前整体的代码结构思路

### 1.1 项目定位和责任边界

Satsuma 是 Host 与隔离 Windows VM 之间的测试执行基础设施。它负责：

- 控制 VMware VM 的启动、停止和快照恢复。
- 将 Host 构建产物物化为带哈希的任务 Artifact。
- 让 VM Agent 在 Guest 本地目录执行程序。
- 管理进程树、超时、stdout、stderr 和结果文件。
- 保存机器可读执行证据，并向上层 AI 返回平台状态。

Satsuma 不判断被测程序的业务逻辑是否正确。业务断言、测试参数、结果解释和目标项目修改由调用它的
AI 或程序员负责。

### 1.2 双端程序和运行通道

项目构建两个运行程序，共享一个静态核心库：

```text
SatsumaCore（静态库）
  ├── SatsumaHost.exe（宿主机）
  └── SatsumaVM.exe（每台测试 VM）
```

生产运行使用共享文件事实源与 `vmrun` 带外控制，RPC 仅保留为独立诊断入口：

```text
调用方 AI / 程序员
        |
        v
SatsumaHost.exe
  ├── VMware Shared Folder：任务、Artifact、状态、日志和结果
  └── vmrun.exe：VM 电源、快照和 Guest 网络之外的带外控制
        |
        v
SatsumaVM.exe
  ├── 校验并领取任务
  ├── 复制 Artifact 到 Guest 本地工作目录
  ├── 使用 Windows Job Object 执行和超时终止进程树
  └── 原子发布 execution.json、日志和收集文件

可选诊断：SatsumaHost serve <--- coro_rpc ---> SatsumaVM --rpc-once
```

共享目录是唯一任务事实来源；`--watch` 和 Windows Service 不启动、不调用也不等待 RPC。`vmrun` 用于
VM 生命周期和最终带外恢复。现有 RPC DTO、Server 与 `--rpc-once` 仅用于诊断和未来可选通知研究。

### 1.4 当前运行目录模型

Host 为每次任务创建唯一 `run_id`，先在点号前缀暂存目录中完成写入，再整体发布为 Agent 可见目录：

```text
shared_folder.host_root/runs/<run_id>/
├── task.json
├── artifacts/
│   └── <vm-id>/...
├── state/
│   ├── <vm-id>/<step-id>.claim.json
│   └── <vm-id>-agent.json
└── results/
    └── <vm-id>/<step-id>/
        ├── execution.json
        ├── stdout.log
        ├── stderr.log
        └── files/...
```

`claim.json` 通过独占创建避免同一步骤被多个 Agent 会话重复领取。Artifact 先在共享目录校验哈希，
再复制到 `agent.json` 的 `local_work_root/<run_id>/` 执行，不直接从 UNC 路径运行程序。

### 2.3 Host 文件任务闭环

- `run` 能读取任务文件、校验 VM 引用并生成唯一或调用方指定的 `run_id`。
- Host 能复制 Artifact、计算实际 SHA-256，并验证可选的预填哈希。
- Artifact 目标被限制在 `artifacts/` 子目录。
- 运行目录在隐藏暂存阶段准备完成后一次性发布，Agent 不会读取半成品 manifest。
- `report` 能统计预期、已报告、成功和失败步骤，并返回执行明细。
- Controller 同时支持从 JSON 文件和内存任务计划物化运行，供主动检测复用。

### 2.4 VM Agent 执行闭环

- Agent 能扫描共享目录并只处理匹配 `lab_id`、protocol 和 `vm_id` 的步骤。
- Agent 能独占创建 claim，避免正常并发场景下的重复领取。
- Agent 能校验 Artifact 哈希，复制到 Guest 本地目录后执行。
- `echo` 步骤能生成无害 stdout 结果。
- `execute` 步骤支持参数数组、本地工作目录和有限超时。
- Windows Job Object 能在超时时终止被测进程树。
- stdout/stderr 使用 `.partial` 文件写入，完成后原子发布最终日志。
- Agent 能收集任务声明的结果文件并记录 SHA-256。
- `execution.json` 记录状态、退出码、超时、耗时、日志路径、错误和收集文件。
- `--watch` 只扫描共享目录，不启动 RPC 客户端，也不等待 Host Server。
- Agent、Artifact 复制、步骤循环和 ProcessRunner 支持 `std::stop_token` 取消。
- Service STOP/SHUTDOWN 可取消运行中的 Job Object；结果固定写入失败状态和 `Agent stop requested`。

### 2.5 RPC 诊断入口

- 已定义版本化的 Agent 注册、心跳、任务轮询和 Job 状态 DTO。
- Host 能校验 `lab_id`、`vm_id`、Agent 版本、`session_id` 和 `boot_id`。
- 诊断客户端能注册、心跳、接收任务引用并上报运行/完成状态。
- Host `serve` 能在 `lab.json` 指定的地址启动 `coro_rpc` Server。
- 已有本机回环测试覆盖 RPC 注册、状态、任务发现和结果上报。
- `--rpc-once` 是唯一保留的 VM 侧 RPC 入口；`--watch` 与 `--service` 完全不使用该通道。
- 该实现冻结为非生产诊断能力，不作为文件任务成功、取消或恢复的判定依据。

### 2.6 VMware 带外控制和快照保护

- `vmrun list` 运行状态查询。
- VM 无界面启动。
- VM 软关闭和硬关闭。
- 恢复指定快照。
- 查询快照列表、创建快照和删除快照。
- `vmrun` 通过 `CreateProcessW` 接收结构化参数，不使用拼接的 `cmd /c`。
- `vmrun` 进程受超时和 Job Object 约束。
- 用户基础快照与 AI 派生快照有不同所有权。
- AI 快照使用配置前缀、时间戳和数量配额。
- Host 拒绝删除用户基础快照或非 AI 所有权快照。
- AI 快照创建/删除状态会写入 `archive_root/snapshots/<vm-id>/` 元数据。
- 已提供默认关闭的真实 VMware 生命周期 smoke 目标，要求显式确认字符串后才允许运行。

### 2.7 Guest 无人值守启动

- `SatsumaVM --install-service` 创建或更新 `SatsumaVM` Service，并返回实际 Service PID。
- Service 使用 LocalSystem、延迟自动启动，以及 5/15/60 秒失败重启和 non-crash failure actions。
- SCM 命令固定为本机安装中的
  `"<install-root>\bin\SatsumaVM.exe" --config <install-root>\agent.json --service`。
- STOP/SHUTDOWN 先请求取消；Agent 清理和退出码确定后，`SERVICE_STOPPED` 恰好最后上报一次。
- 安装和更新只写入当前所需配置，不保存或恢复完整 SCM 快照、DACL 或 owner。
- 停止逻辑会处理 `START_PENDING`/`STOP_PENDING` 并有限等待；安装等待 `RUNNING` 和有效 PID。
- `--remove-service` 有限等待停止、关闭删除句柄并等待 SCM 对象真正消失；Service 不存在时幂等返回。
- `SatsumaVM --validate-config` 只做配置解析预检，不会创建任务或访问 VMware。
- `--once`、`--watch` 和 `--rpc-once` 不修改 SCM 或系统启动配置。
- `install-agent.ps1` 能自动请求 UAC、串行安装、复制并校验固定 `.new` 文件、停止 Service、迁移旧任务、
  切换文件并启动 Service；失败时只做一次简单文件恢复，复杂故障使用 Guest 快照。
- 安装成功后删除 `.bak`、`.new` 和配置暂存文件，不永久保留旧版本。
- `--watch` 与 Service 容忍 Shared Folder 暂时不可用，避免 VMware Tools 启动竞态导致进程退出。
- Agent 会在共享目录发布带 PID 的 `agents/<vm-id>.json` 就绪状态，供安装脚本和诊断核对实际进程。

### 2.8 AI 主动检测模式

`SatsumaHost check` 已实现以下检查：

- Host 共享目录是否存在并支持原子写入。
- Host 归档目录是否存在并支持原子写入。
- `vmrun.exe` 是否存在。
- `vmrun list` 是否能执行。
- 目标 VMX 是否存在。
- 快照列表是否包含配置的用户基础快照。
- 自动发布唯一 echo 任务并等待目标 Agent 返回。
- 校验 Agent 结果状态、退出码、超时标记和 stdout 内容。

报告区分：

- `ready` / 退出码 0：环境与 Agent 探针均正常。
- `degraded` / 退出码 3：Agent 探针正常，但某项 VMware/Host 环境检查失败。
- `failed` / 退出码 1：Agent 超时、结果失败或内容不匹配。

  根因是 `RpcClient::disconnect()` 对已失效 executor 执行无超时同步 drain。`2ee81ae` 已改为有限等待的
  独立清理线程，并增加 Server 停止、同端口重启和 Client 重连测试。
- Guest 安装 `SatsumaVM-rpc-reconnect-202607260940.exe` 后，claim v2 与诊断 `retry_safe=true` 均通过；
  但真实强杀 Server 时 presence 只再更新一次便停止，证明阻塞发生在第三方 `call_for` 内部，而不是随后
  的 `disconnect()` drain。
- Guest 安装 `SatsumaVM-rpc-hard-timeout-202607261015.exe` 时，计划任务进程未产生 presence 并触发安装
  回滚；同一二进制在 Guest 前台执行 `--rpc-once` 返回 `0xC0000005`。该结果证明 `e6b315e` 的每次调用
  临时线程破坏了第三方 Client 的线程约束，不能作为外层硬超时实现。
- `ca819ca` 曾恢复同线程同步 `call_for`，并把 watch 模式拆分为文件主循环、RPC 专用线程和独立 watchdog；
  文件线程只把 Job 状态放入有限队列，RPC 永久卡死时进程以 `ERROR_TIMEOUT` 退出并由计划任务重启。
  当时 Debug/Release 均通过 7/7，本机 Release `--rpc-once` 返回 0。候选
  `SatsumaVM-rpc-thread-isolation-202607261851.exe` 的 SHA-256 为
  `327F40335CAB5D1DF6AC7F0428226237EEB19739FA038E9D0D0B4FE1D0937AB6`，对应安装脚本为
  `install-agent-rpc-thread-isolation-202607261851.ps1`；该候选现已废弃，不再进入 Guest 验收。
- `1b0937d` 将 `--watch` 完全切换为可取消的纯文件通道；RPC 阻塞不再影响任务正确性或 Agent 退出。
- `06993f7` 与 `2bfed66` 接入并加固 Windows Service，完成终态顺序、STOP 竞态、严格所有权/DACL、
  START_PENDING、既有 Service 全量回滚和损坏配置卸载处理。
- `e06eed5` 将安装脚本迁移为事务化 Service 安装，并增加 SCM/PID/命令/presence 持续健康门槛和旧计划
  任务迁移。当前代码已通过 Debug/Release 10/10、Windows PowerShell 5.1/PowerShell 7 Parser、编码和
  差异守护；由于当前终端不是管理员，真实 SCM 与 Guest 安装留给稳定候选后的独立验收。

## 3. 还没有做完的部分

### 3.1 真实实验室仍缺少的验收

- 当前仅验收一台 NAT/DHCP Windows VM，尚未完成 Client/Gateway 双 VM 编排。
- 当前 Windows Service 候选尚未在管理员 SCM、真实 Guest 或快照恢复后自动上线场景中验收。
- 尚未验证危险测试专用的 Host-only/LAN Segment 隔离网络。
- 旧计划任务候选已真实执行软关机、硬关机、恢复 AI 快照、重新启动和 Agent 自动上线。
- 已接入独立于 Satsuma 的 `SatsumaDemoApp.exe` 验收 Artifact、参数、日志和结果收集；尚未接入用户实际
  业务项目和业务断言。
- 已完成连续 20 次真实任务测试；更长时间稳定性和共享目录瞬断仍待后续故障注入覆盖。

### 3.2 JSON 任务生命周期不完整

单 VM 的 `restore_before`、启动、Agent Ready、部署、执行、收集、`finally`、成功/失败清理和
`RECOVERY_FAILED` 已接入 `orchestrate`。仍未实现：

- Host 崩溃后根据持久化阶段自动续跑或转入正式人工确认状态。
- 跨步骤的重试、退避和幂等策略。
- 多 VM 操作的独立状态、部分恢复和统一 teardown。

### 3.3 多 VM 编排能力有限

- 多台 Agent 可以各自领取属于自己的步骤，但 Host 尚无显式依赖图和跨 VM 屏障。
- 尚不支持“Gateway 先启动并 Ready，再执行 Client”的依赖语义。
- 尚不支持后台步骤、长期服务、显式 stop、wait-ready 或健康检查步骤。
- 尚不支持并行度、失败传播和多 VM 统一 teardown 策略。

### 3.4 崩溃恢复和 claim 租约仍需完善

claim v2 已记录有限租约、attempt、`session_id`、`boot_id` 和 `retry_safe`。过期后只有启动身份变化且
显式安全的步骤会原子归档旧 claim 并重试；其他步骤生成 Host 可见的人工门禁。尚缺：

- Host 对失联 Agent 的任务回收决策。
- Host 自身崩溃后根据持久化阶段、VM 状态和 Agent 身份决定续跑或保持门禁。
- 长时间步骤的主动续租；当前租约按步骤超时加固定缓冲一次性计算。

### 3.5 运行归档和报告仍是最小版本

- `orchestrate` 已自动归档主任务和 `finally` 的不可覆盖证据；普通 `run` 尚未自动归档。
- `report` 支持可选的 `--wait-seconds` 有限等待；尚未形成跨命令统一超时参数。
- 尚未生成完整 Host 操作日志、vmrun 日志和恢复报告。
- 尚未实现归档保留期、空间配额、清理策略和证据只读保护。
- 尚未实现面向多个运行的查询、索引或历史摘要。

### 3.6 发布与兼容安全仍需完善

- RPC 当前没有 TLS、身份凭据或消息签名，因此只保留为非生产诊断入口。
- 普通可信测试已验证 NAT 网络；危险测试仍应使用 Host-only/LAN Segment 和防火墙作用域隔离。
- 尚未实现密钥轮换、Host 身份固定或 Guest 凭据存储。
- 已实现受保护安装布局、Windows Service、事务升级、旧计划任务迁移和失败回滚。
- 尚未形成签名安装包、版本清单和独立发布渠道。
- 尚未实现配置版本迁移和 Host/Agent 升级兼容矩阵。

### 3.7 CLI 和诊断仍有缺口

- 尚未实现设计稿中的细粒度 `file push`、`exec`、`status`、`wait` 等交互命令。
- `check` 不会自动启动 VM 或 Agent。
- `check` 尚未单独报告 VMware Tools 版本、Guest Tools 响应和 Agent 二进制哈希。
- `management_ip` 是可选元数据，NAT/DHCP 环境可以省略；主动检测不依赖该字段。
- JSON Schema 已提供，但运行时主要使用 C++ 手写校验，需要持续保证两者一致。
- 错误码和错误 JSON 尚未形成覆盖所有 CLI 失败场景的统一协议。

### 3.8 测试覆盖仍需扩展

- 旧计划任务候选已执行真实单 VM VMware 测试；当前 Service 候选尚未执行真实 SCM/Guest 测试。
- 尚无真实双 VM 时序、断网、Guest 卡死、Tools 失效和恢复快照测试。
- 尚无 Agent claim 后崩溃、Host 中途重启、磁盘满和共享目录瞬断测试。
- mailbox 协议及其损坏/恶意消息测试尚未实现；恶意/损坏 manifest 和版本升级兼容矩阵也尚未实现。
- 尚无长时间稳定性、重复 20 次以上真实任务和大 Artifact 压力测试。
- 当前只支持 Windows/MSVC，尚无其他平台目标。

## 4. 需要程序员或用户手动配合的部分

完整步骤见 [SatsumaReadme.md](SatsumaReadme.md)。以下事项无法在当前无 VMware GUI、无 Guest 控制
和无管理员权限的命令行环境中可靠完成。

### 4.1 Host 上的人工准备

1. 安装并许可 VMware Workstation，确认真实 `vmrun.exe` 路径。
2. 确定仓库、共享目录、归档目录和 VMX 的真实绝对路径。
3. 确定 Guest 可达的 VMware NAT 或 Host-only Host 地址。
4. 生产文件通道不开放 TCP 端口；只有显式 RPC 诊断需要 TCP 37100，并应仅放行对应 VMware 网段。
5. 检查磁盘空间，确保共享目录和归档目录不包含源码、用户目录或凭据。
6. 将确认后的真实值写入已忽略的 `lab.local.json`。

### 4.2 VMware GUI 中的人工准备

1. 创建或选择任意可丢弃的 Windows 测试 VM，不要求特定名称。
2. 安装 VMware Tools。
3. 普通测试可保留 NAT/DHCP；危险网络测试再添加隔离实验网卡。
4. 为每台 VM 添加相同的专用 Shared Folder，并选择始终启用。
5. 确认每台 VM 的 `.vmx` 文件绝对路径。
6. 建议从干净基础 VM 克隆出 Client、Gateway 等实例。

### 4.3 每台 Guest VM 内的人工准备

1. 为当前 VM 创建独立 `agent.json`，设置唯一逻辑 `vm_id`。
2. 验证 Guest 能读写 `\\vmware-host\Shared Folders\<share-name>`。
3. 执行一次 `scripts/install-agent.ps1` 并确认 UAC；脚本完成事务安装、Service 注册、健康验证和旧任务迁移。
4. 清理遗留测试进程、路由、DNS、适配器和临时文件。

### 4.4 用户基础快照

1. 确认 VMware Tools、管理网络、Shared Folder 和 Agent 均已验证。
2. 确认没有运行中的 Satsuma Job 或被测程序。
3. 推荐关闭 VM 后创建 `clean` 基础快照。
4. 将快照名写入 `lab.local.json` 的 `vms[].snapshots.base`。
5. 基础快照只能由用户维护，AI 不应覆盖或删除。

### 4.5 真实验收需要一次性授权

建议按以下顺序进行：

1. 将目标 VM 声明为可丢弃测试机，并授权 Satsuma 对其执行启停和快照恢复。
2. 启动 VM，等待 Windows Service 自动启动 Agent 并持续发布 presence。
3. 对单台 VM 执行 `SatsumaHost check --vm <id>`。
4. 对全部 VM 执行不带 `--vm` 的主动检测。
5. 连续运行无害 echo 任务，确认没有丢失、重复和超时。
6. 运行一个可丢弃的真实测试 Artifact，检查日志、退出码和收集文件。
7. 显式启用并运行 `SatsumaRealVmwareSmoke`；已有实验室授权范围内不再逐次询问用户。

### 4.6 目标项目接入时需要程序员提供

- 明确的测试程序绝对路径和构建方式。
- 每个程序的参数、预期退出码和最大运行时间。
- 应收集的日志、JSON、抓包或其他结果文件相对路径。
- 业务通过/失败的判断规则。
- 测试是否会安装驱动、修改路由/DNS/防火墙或要求重启。
- 测试前后需要的快照和人工安全边界。

## 6. 建议的下一步

当前优先级最高的是把文件控制 mailbox 作为一个完整协议里程碑实现，避免形成只有 Guest 扫描器的
半条协议。该里程碑必须同时包含 Host 原子写入、单调 sequence、Agent ACK、启动补偿扫描，以及
stop/cancel 的持久证据。完成后再继续阶段 1 的失联判断和 Host 崩溃续跑门禁。

在真实环境准备之前，代码侧可以并行推进但不依赖 VMware 的部分包括：

1. Host/Agent 双端 mailbox、单调 sequence、ACK、启动补偿和 stop/cancel 证据。
2. Host 崩溃后按生命周期状态决定续跑或人工门禁。
3. Agent 中断与 Service stop/cancel 的编排故障注入。
4. claim 主动续租和 Host 失联判断。
5. 统一错误 JSON 和跨命令超时语义。

用户需要一次性确认哪些 VM 可被丢弃和恢复。确认后，AI 可以在配置范围内自主启停和恢复，不应逐次
打断用户；基础快照删除、未知 VM、防火墙和网络拓扑修改仍需要新的明确授权。
