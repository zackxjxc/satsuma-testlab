# 文件协议

## 协议原则

Shared Folder 是任务与结果的唯一事实源。协议依赖同卷原子改名和不可变证据，不依赖消息送达顺序或常驻
连接。Host 只发布完整目录，Agent 只发布自己仍持有 claim 的规范结果。

生产 Agent 使用运行清单协议 v2。加载器保留 v1 读取能力，只用于旧 Agent 更新到 v2；新的任务与配置不应
生成 v1。

## 目录布局

```text
<shared-root>/
├── agents/
│   ├── <hardware-id>.json
│   ├── <hardware-id>.binding.json       # Host 确认的业务角色
│   ├── <old-hardware-id>.migrated.json  # 可选硬件变化证据
│   └── sessions/<hardware-id>/<session-id>.json
├── runs/
│   ├── .preparing-*/
│   └── <run-id>/
│       ├── task.json
│       ├── cancel.json                 # 可选
│       ├── artifacts/...
│       ├── state/
│       │   ├── <vm-id>-agent.json
│       │   ├── <vm-id>-agent-error.json
│       │   └── <vm-id>/<step-id>.claim*.json
│       └── results/<vm-id>/<step-id>/
│           ├── execution.json
│           ├── stdout.log
│           ├── stderr.log
│           └── files/...
└── updates/
    └── <vm-id>/<update-id>/
        ├── update.json
        ├── SatsumaVM.exe
        └── result.json
```

点号前缀目录和文件是未完成事务或取证数据，不属于规范任务入口。运行目录、VM ID、步骤 ID 和更新 ID 都
必须满足 `^[A-Za-z0-9_-]{1,128}$`。

## Schema

| 文件 | Schema | 生产者 | 消费者 |
|---|---|---|---|
| Host 配置 | `lab.schema.json` | 操作者 | Host |
| Agent 配置 | `agent.schema.json` | 操作者/更新器 | Agent |
| 用户任务 | `task.schema.json` | 操作者 | Host |
| `task.json` | `run-manifest.schema.json` | Host | Agent/Host |
| presence | `presence.schema.json` | Agent | Host |
| claim/续租 | `claim.schema.json` | Agent | Agent/Host |
| `cancel.json` | `cancel.schema.json` | Host | Agent |
| `execution.json` | `result.schema.json` | Agent | Host |
| 运行报告 | `report.schema.json` | Host | 操作者 |
| Agent 更新 | `update.schema.json` | Host/Agent | Agent/Host |
| 编排状态 | `lifecycle.schema.json` | Host | Host |

所有 Schema 使用 JSON Schema Draft 2020-12。CI 先执行 metaschema 校验，再用配置和任务示例验证公开输入。

## 运行清单

Host 将用户任务物化为不可变 `task.json`：

- 加入 `protocol_version=2`、`lab_id`、`run_id`、`request_id` 和 `created_at`。
- 把 Artifact 的 Host `source` 转换为运行目录内 `path` 和实际 SHA-256。
- 为每个步骤补齐 `timeout_seconds`、`retry_safe`、参数和收集文件默认值。
- v2 `execute` 必须带 `run_as`；`echo` 固定为 SYSTEM。

正式运行目录出现后，不允许修改 `task.json` 或 Artifact。需要更改任务时必须创建新的 `run_id`。

## Claim 租约

当前基础 claim Schema 版本为 3；加载器兼容读取不带续租字段的 v2 历史证据。v3 包含：

- 稳定范围：`run_id`、`vm_id`、`step_id`。
- 所有权：`job_id`、`session_id`、`boot_id`、`attempt`。
- 时间：领取、最近续租和租约截止的 Unix 毫秒及 UTC 文本。
- 策略：`retry_safe` 与单调递增 `renewal_sequence`。

Agent 通过步骤专用锁发布基础 claim。续租写入包含 job 和序号的不可变 sidecar；读取者按连续序列合成有效
租约。发布结果时再次检查 job、attempt、续租序列和截止时间，形成 fencing。

过期且 `retry_safe=true` 的 claim 会被归档后重新领取。非安全步骤会写
`<step-id>.claim-recovery.json`，Host 报告将其提升为 `manual_intervention_required`。

## 执行结果

`execution.json` 是步骤完成的唯一规范标志。状态：

| `status` | 含义 |
|---|---|
| `exited` | 进程正常结束；是否业务成功继续看 `exit_code` 是否为 0 |
| `timed_out` | 超时后终止进程树 |
| `failed` | 启动、取消、容量、身份、文件或 Agent 内部错误 |

结果记录实际请求的 `run_as`。成功的 `interactive_user` 结果必须带 `interactive_session_id`；SYSTEM 结果不得
携带该字段。`stdout`、`stderr` 和 `files[].path` 都是运行目录内相对路径，并带收集文件 SHA-256。

Agent 先在 `.jobs/<job-id>` 写日志和结果文件，取得 claim 锁后再发布到规范位置。失权进程保留取证目录，
不会覆盖当前 owner 的结果。

## Presence 与状态

`agents/<hardware-id>.json` 记录 SMBIOS UUID、业务 VM ID、实验室、协议、版本、更新 ID、Session、Boot、PID、
状态和更新时间。新 Agent 尚未绑定业务角色或检测到硬件变化时发布 `unbound`；Host 只在 UUID、VM ID、版本和
状态均匹配时接受它。旧版显式 `vm_id` 配置还会发布 `<vm-id>.json` 兼容别名。

若兼容别名显示多个业务 VM 同时声明同一个 UUID，`discover` 返回 `identity_conflict`，绑定和 `check` 均拒绝
继续。无业务别名的新 Agent 还会按 Session 发布 heartbeat；同一 UUID 在两分钟内存在多个活跃 Session 时也
触发冲突。该状态表示 VMware 克隆保留了重复虚拟硬件身份，必须先在虚拟化层修复。

`<hardware-id>.binding.json` 由 Host 写入，未显式配置 `vm_id` 的 Agent 在轮询时读取它并切换到对应业务角色。
硬件变化时旧 UUID 的迁移记录保留 `old_vm_id`，但不会自动继承绑定，必须由操作者确认。

运行内 `<vm-id>-agent.json` 表示该 Agent 的 `idle`/`running` 状态。无法加载某个运行时，Agent 最佳努力写
`<vm-id>-agent-error.json`，其中包含错误与观察时间；该诊断文件不等于步骤结果。

## 取消

`cancel.json` 包含 `run_id`、非空 `reason` 和 `requested_at`。Agent 只接受 Schema 版本和目录运行 ID 都匹配
的请求。文件存在后，该运行的执行停止令牌保持有效；取消不可撤销，重试需要新建运行。

## 容量限制

| 对象 | 上限 |
|---|---:|
| 每运行 Artifact | 256 个 |
| 每运行步骤 | 256 个 |
| 每步骤参数 | 256 个 |
| 每步骤收集文件 | 128 个 |
| 单 Artifact | 2 GiB |
| 单收集文件 | 512 MiB |
| 单步骤收集总量 | 2 GiB |
| stdout + stderr | 64 MiB |

Host 在复制前检查 Artifact 大小，Agent 在共享端和本机端复核大小与 SHA-256。进程执行期间每约 100ms 检查
日志总量，快速退出后还会做最终校验，避免竞态绕过上限。

## 报告语义

Host 只读取清单声明的规范结果路径，不递归搜索任意 `execution.json`。报告状态：

- `pending`：至少一个规范结果缺失，且没有人工门禁。
- `succeeded`：全部步骤完成，且每个 `exited` 的退出码均为 0。
- `failed`：全部步骤完成，但至少一个步骤失败、超时或返回非零。
- `manual_intervention_required`：存在无法自动恢复的 claim 状态，优先级高于 pending。

`complete=true` 仅表示收齐全部规范结果。等待超时由 CLI 附加 `wait_status=timeout`，不会篡改运行本身的
`status`。
