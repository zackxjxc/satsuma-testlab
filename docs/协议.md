# VMCI 传输协议

## 协议原则

Host 的 `transport.state_root` 是任务与结果的唯一事实源，Guest 的 `<storage_root>/mirror` 是可重建的本地
镜像。Agent 通过 `vmci://<host-cid>:<port>` 使用 ZMQ REQ/REP 与常驻网关通信；Guest 网卡、IP、DNS、VPN
和网络驱动不参与传输。Host 只公布完整文件，Agent 只发布自己仍持有 claim 的规范结果。

请求元数据上限为 4 MiB，二进制负载固定按不超过 1 MiB 的块传输。每个下载或上传在提交前核对总大小和
SHA-256；断线后的 REQ socket 会重建，未完成上传留在 Host `.transfers` 暂存区，不会成为规范结果。

生产 Agent 只接受运行清单协议 v4。用户任务只接受当前 schema 3，由 Host 物化为
schema 2 的 v4 运行清单。

## 本地状态布局

```text
<transport.state_root>/                 # Host 权威状态
├── agents/
│   ├── <hardware-id>.json
│   ├── <hardware-id>.inventory.json
│   ├── <hardware-id>.inventory-refresh.json # Host 显式刷新请求
│   ├── <hardware-id>.binding.json       # Host 确认的 VM 标识
│   ├── <old-hardware-id>.migrated.json  # 可选硬件变化证据
│   └── sessions/<hardware-id>/<session-id>.json
├── runs/
│   ├── .preparing-*/
│   └── <run-id>/
│       ├── task.json
│       ├── cancel.json                 # 可选
│       ├── .artifacts/<index>.bin      # 新运行：按不可变清单的零起序号存储
│       ├── state/
│       │   ├── <vm-id>-agent.json
│       │   ├── <vm-id>-agent-error.json
│       │   ├── <vm-id>-cleanup-request.json
│       │   ├── <vm-id>-cleanup.json
│       │   └── <vm-id>/<step-id>.claim*.json
│       └── results/<vm-id>/<step-id>/
│           ├── execution.json
│           ├── stdout.log
│           ├── stderr.log
│           └── files/...
└── updates/
    └── <vm-id>/<update-id>/
        ├── update.json
        ├── SatsumaVM.exe
        └── result.json
```

`.artifacts` 是 Host 内部文件存储，不是 Guest 任务路径；其他事务暂存目录也不属于可执行任务入口。运行目录、VM ID、步骤 ID 和更新 ID 都
必须满足 `^[A-Za-z0-9_-]{1,128}$`。

清单中的 Artifact `path` 仍是 `artifacts/...`，网关根据已验证的 VM、路径和清单序号读取物理文件；Guest
继续按逻辑路径下载和执行。不同 VM 可以声明相同目标路径和不同内容，同一 VM 的重复目标仍被拒绝。
没有 `.artifacts` 的旧运行继续读取原 `artifacts/...` 布局；新运行缺少某个序号文件时不会回退或复用其他文件。

Guest 的镜像仍按登记身份隔离，新执行尝试的证据改为 `<storage_root>/staging/<job-id>/`。其中
`attempt.json` 保存完整归属，`files/...` 保存收集副本，SYSTEM 日志直接写入该尝试目录。
Host 规范结果保持 `runs/<run-id>/results/<vm-id>/<step-id>/`。具体布局见[短路径存储设计](短路径存储设计.md)。

## Schema

| 文件 | Schema | 生产者 | 消费者 |
|---|---|---|---|
| Host 配置 | `lab.schema.json` | 操作者 | Host |
| Agent 配置 | `agent.schema.json` | 操作者/更新器 | Agent |
| 用户任务 | `task.schema.json` | 操作者 | Host |
| `task.json` | `run-manifest.schema.json` | Host | Agent/Host |
| presence | `presence.schema.json` | Agent | Host |
| inventory | `inventory.schema.json` | Agent | Host |
| claim/续租 | `claim.schema.json` | Agent | Agent/Host |
| `cancel.json` | `cancel.schema.json` | Host | Agent |
| `execution.json` | `result.schema.json` | Agent | Host |
| 运行报告 | `report.schema.json` | Host | 操作者 |
| Agent 更新 | `update.schema.json` | Host/Agent | Agent/Host |
| 编排状态 | `lifecycle.schema.json` | Host | Host |

所有 Schema 使用 JSON Schema Draft 2020-12。CI 先执行 metaschema 校验，再用配置和任务示例验证公开输入。

## 运行清单

Host 将用户任务物化为不可变 `task.json`：

- 加入 `protocol_version=4`、`lab_id`、`run_id` 和 `created_at`。
- 把 Artifact 的 Host `source` 转换为 Guest 逻辑 `path` 和实际 SHA-256；Host 物理存储位置不写入清单。
- 为 `execute`/`script` 补齐 `timeout_seconds`、参数和收集文件默认值，为所有步骤补齐 `retry_safe`。
- v4 `execute`/`script` 必须带 `run_as`；`echo` 固定为 SYSTEM，不接受无效的超时字段。

`script` 必须精确匹配同一 VM Artifact。engine 固定为 `cmd`、`windows_powershell` 或 `pwsh`，解释器绝对
路径只能来自 inventory，不能由任务提供。参数仍是 JSON 字符串数组；Agent 复用 execute 的 Job Object、超时、
取消、claim、fencing、日志和文件收集路径。

正式运行目录出现后，不允许修改 `task.json` 或 Artifact。需要更改任务时必须创建新的 `run_id`。

## Claim 租约

当前 claim Schema 版本为 3，并且只接受该版本。它包含：

- 稳定范围：`run_id`、`vm_id`、`step_id`。
- 所有权：`job_id`、`session_id`、`boot_id`、`attempt`。
- 时间：领取、最近续租和租约截止的 Unix 毫秒及 UTC 文本。
- 策略：`retry_safe` 与单调递增 `renewal_sequence`。

Agent 通过 VMCI 请求 Host 网关领取 claim。网关是唯一写入者，续租直接原子替换单份权威记录；重复的续租
请求按当前序号幂等返回。发布结果时再次检查 job、attempt 和截止时间，形成 fencing。

过期且 `retry_safe=true` 的 claim 会被归档后重新领取。非安全步骤会写
`<step-id>.claim-recovery.json`，Host 报告将其提升为 `manual_intervention_required`。

## 执行结果

`execution.json` 是步骤完成的唯一规范标志。状态：

| `status` | 含义 |
|---|---|
| `exited` | 进程正常结束；是否业务成功继续看 `exit_code` 是否为 0 |
| `timed_out` | 超时后终止进程树 |
| `failed` | 启动、取消、容量、身份、文件或 Agent 内部错误 |

结果记录实际请求的 `run_as`。成功的 `interactive_user` 结果必须带 `interactive_session_id`；SYSTEM 结果不得
携带该字段。`stdout`、`stderr` 和 `files[].path` 都是运行目录内相对路径，并带收集文件 SHA-256。

执行结果继续使用 schema 2，不增加过程状态或证据状态字段。SYSTEM 进程的 stdout/stderr 写入
`<storage_root>/staging/<job-id>/`；交互用户日志保留原工作目录与 ACL，结束后复制到此证据区。
Agent 通过网关核对 Host 权威 claim 后，再上传并提交规范结果。VMCI 短暂中断不破坏进程日志句柄，
失权进程不能覆盖当前 owner 的结果。

证据上传失败时，Agent 保留本地原日志、`execution.json` 和 `diagnostic.json`，只在原 claim 内尝试补发
失败摘要，不重新执行程序。摘要的 `stdout`、`stderr` 为空，`files` 为空数组，已经取得的 `exit_code`
仍保留。完全失联、claim 过期或失权时不能伪造规范结果；非安全步骤仍受人工恢复门禁保护。

## Presence 与状态

`agents/<hardware-id>.json` 记录 SMBIOS UUID、稳定 VM 标识、实验室、协议、版本、更新 ID、Session、Boot、PID、
状态、更新时间以及 inventory 的观察时间和 SHA-256 引用。新 Agent 尚未绑定 VM 标识或检测到硬件
变化时发布 `unbound`；Host 只在 UUID、VM ID、版本和状态均匹配时接受它。旧版显式 `vm_id` 配置还会发布
`<vm-id>.json` 兼容别名。

`<hardware-id>.inventory.json` 是当前 Agent 进程会话首次成功访问 VMCI 通道时采集的环境快照，包含 Windows
版本/架构、固定盘容量、内存和三个固定脚本 engine。成功后普通心跳只验证文件与摘要；丢失或篡改时用内存
缓存补发，不重新探测系统。Agent 重启或匹配的显式 refresh 请求才重新采集，并更新 `observed_at` 和摘要。

若兼容别名显示多个 VM 标识同时声明同一个 UUID，`discover` 返回 `identity_conflict`，绑定和 `check` 均拒绝
继续。没有 VM 标识别名的新 Agent 还会按 Session 发布 heartbeat；同一 UUID 在两分钟内存在多个活跃 Session 时也
触发冲突。该状态表示 VMware 克隆保留了重复虚拟硬件身份，必须先在虚拟化层修复。

通用 Agent 省略安装配置中的 `lab_id`，每轮同步前发送 `enroll`。该扩展使用 `enrollment_version=1`，
不改变任务协议 `protocol_version=4`。请求包含硬件 UUID、会话 ID、当前版本与二进制 SHA-256，无需预设实验室。
Host 只接收硬件清单中获准的 UUID，返回 `lab_id`、中性 `vm_id` 和 `enrollment_id`。
版本/哈希依然由 `check` 校验，不因登记而信任 Agent 的自报值；登记通道保留受控更新能力。

`<state-root>/.enrollment.json` 持久保存 Host 状态空间标识，网关重启复用；创建新状态根产生新标识。
通用 Agent 的后续请求携带该标识，旧状态空间的请求被拒绝。Guest 将镜像和工作目录分别放在
`<mirror-root>/enrolled/<enrollment-id>`、`<storage-root>/work/enrolled/<enrollment-id>`，不混用旧运行数据。
`<storage-root>/agent/enrollment-cache.json` 仅供重启/自更新定位缓存；每次执行前仍须在线登记和同步，缓存不能授权离线执行。
此机制面向可信 VMware 实验室，不是基于证书的双向认证或跨租户安全边界。通用 Agent 的 ID 由 Host 控制，
不支持使用旧式 `agent rebind --next-vm` 改写 Guest 的固定身份配置。

旧式显式配置 `lab_id` 的 Agent 保留兼容流程：`<hardware-id>.binding.json` 由 Host 写入，
未显式配置 `vm_id` 的 Agent 在轮询时读取它并采用对应的 VM 标识。
当 Host 配置已经登记该硬件 UUID（例如由 `init` 从选定 VMX 生成）且绑定记录缺失时，网关在首次 `index`
请求中自动发布对应绑定。未登记的 UUID 不会自动加入 VM 列表；已有绑定记录不会被自动覆盖。此行为也适用于
Agent 从冷快照恢复了旧 VM ID 缓存的情况，但显式 `agent.json.vm_id` 仍需先迁移。
同一硬件重启且绑定文件暂时缺失时，Agent 可从本地缓存恢复最近经 Host 确认的 VM 标识；绑定恢复后仍以 Host
绑定为准。硬件变化时旧 UUID 的迁移记录保留 `old_vm_id`，但不会继承缓存或绑定，必须由操作者确认。

运行内 `<vm-id>-agent.json` 记录该 Agent 对当前运行的处理状态。无法加载某个运行时，Agent 最佳努力写
`<vm-id>-agent-error.json`，其中包含错误与观察时间；该诊断文件不等于步骤结果。
步骤的收集或发布异常通过同一诊断文件的 `status=execution_error` 与 `step_errors` 报告，包含 job/attempt、
`process_status`、`evidence_status`、实际退出码、发布状态及本地证据位置。旧 `invalid_run` 诊断仍可读取。
这些信息通过原诊断通道传输，不改变任务协议 v4 或执行结果 schema 2。

## 清理确认

Host 在归档证据后按任务 `cleanup` 策略写 `<vm-id>-cleanup-request.json`。Agent 只在该 VM 的规范步骤全部完成
后删除 `<storage-root>/work/<lab-id>/<run-id>/<vm-id>`，并原子写 `<vm-id>-cleanup.json`，记录 request ID、
目标、`deleted`/`failed`、删除路径数量、失败路径数量和错误。Host 有限等待匹配回执；失败或超时进入
`RECOVERY_FAILED`，不得释放实验室租约。

Host 状态根运行目录的 `archive_then_delete` 只能在 Host 归档目录已经复制、逐文件 SHA-256 校验并写入
`.archive-complete.json` 后执行。人工介入固定 retain。VM 结束动作为 `restore` 时可跳过 Guest 删除等待，
因为本地工作目录随快照回退；Host 状态根和归档不受 Guest 快照影响。

## 实验室租约

所有 Host 写操作先取得由规范化 `lab_id` 和配置路径摘要生成的 Win32 Mutex，再维护
`<archive-root>/coordination/lab-lease.json`。租约记录 lease ID、Host PID、命令、run ID、状态及取得/续租时间，
活动进程每 2 秒原子续租。`run` 发布后租约继续 active，直到 `runs finalize` 证明运行终态；`orchestrate` 在
完整归档和清理后释放。等待超时、清理失败和人工介入不自动解锁。

## 取消

`cancel.json` 包含 `run_id`、非空 `reason` 和 `requested_at`。Agent 只接受 Schema 版本和目录运行 ID 都匹配
的请求。文件存在后，该运行的执行停止令牌保持有效；取消不可撤销，重试需要新建运行。

## 容量限制

| 对象 | 上限 |
|---|---:|
| 每运行 Artifact | 256 个 |
| 每运行步骤 | 256 个 |
| 每步骤参数 | 256 个 |
| 每步骤收集文件 | 128 个 |
| 单 Artifact | 2 GiB |
| 单收集文件 | 512 MiB |
| 单步骤收集总量 | 2 GiB |
| stdout + stderr | 64 MiB |

Host 在复制前检查 Artifact 大小，Agent 在 Host 描述和本机镜像两侧复核大小与 SHA-256。进程执行期间每约 100ms 检查
日志总量，快速退出后还会做最终校验，避免竞态绕过上限。

## 报告语义

Host 只读取清单声明的规范结果路径，不递归搜索任意 `execution.json`。报告状态：

- `pending`：至少一个规范结果缺失，且没有人工门禁或 Agent 错误。
- `succeeded`：全部步骤完成，且每个 `exited` 的退出码均为 0。
- `failed`：全部步骤完成但存在失败，或规范结果尚未收齐但已有 Agent 错误；必须同时查看 `complete`。
- `manual_intervention_required`：存在无法自动恢复的 claim 状态，优先级高于 pending。

`complete=true` 仅表示收齐全部规范结果。等待超时由 CLI 附加 `wait_status=timeout`，不会篡改运行本身的
`status`。

`report.agent_errors` 汇总运行内的旧 `invalid_run` 和新步骤诊断；不合规诊断作为 `invalid_diagnostic`
报告，不能冒充规范结果。`process_status` 与 `evidence_status` 区分程序执行和证据处理。
`report --wait-seconds` 在未完成运行出现 Agent 错误时提前返回 `wait_status=agent_error`、退出码 1，
但不释放实验室租约。生命周期编排仍等待完整结果或人工门禁，不能根据这个提前报告跳过安全收尾。
