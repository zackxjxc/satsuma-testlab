# 验收与测试边界

Satsuma 的验收对象是测试工具本身：安装、服务、VMCI、任务执行、文件收集和虚拟机生命周期。
使用独立的无害夹具验证这些能力，不依赖某个使用者项目，也不把使用者程序的成功或失败当作工具的验收结论。

## 三层证据

1. 本地自动回归：`ctest --preset windows-debug` 和 `ctest --preset windows-release`。
   默认测试不修改真实 VMware；覆盖文件与配置、令牌与 Job、版本比较、安装锁、更新、claim、报告及协议。
2. 真实 VM 验收：使用已授权的 VMX 和快照，记录发行 EXE 的哈希、构建身份、任务、报告、归档和最终电源状态。
3. 人工界面验收：验证 UAC 安全桌面、双击窗口交接和关闭行为。SYSTEM 下无参数调用 EXE 可以验证安装逻辑，
   但不能代替普通用户点击 UAC 的界面证据。

报告必须区分“已实现”“本地测试通过”“真实 VM 通过”和“未覆盖”。脚本主动返回非零退出码、证据收集失败、
传输中断和 Agent 崩溃是不同场景，不能用其中一个代替其余场景。

## 安装与升级矩阵

| 场景 | 必须核对的结果 |
| --- | --- |
| 无安装、单 EXE 无参数启动 | 创建本机配置，服务 Running / Auto / LocalSystem，配置无预置 lab_id、vm_id |
| 已安装版本与哈希完全一致 | 成功显示状态，EXE/配置不覆盖，服务 PID 不变化 |
| 已安装版本更高 | 不降级、不替换、不重启服务 |
| 已安装版本更低 | 更新到候选版本，服务恢复运行 |
| 版本相同、哈希不同 | 更新到候选字节，保留本机配置与身份 |
| 候选 EXE 损坏 | 明确拒绝；首次安装不创建安装根，已有安装不停止服务 |
| 安装锁已被其他进程持有 | 第二个进程失败，已有安装保持可用 |
| 替换文件失败、新服务启动后失败 | 报告失败，核对旧 EXE、配置、服务及事务文件，而不只看日志文本 |
| 存在未完成事务 | 拒绝继续覆盖，保留事务文件和可诊断的错误 |
| 同名未知服务或任务 | 拒绝接管，定义保持不变 |
| 已确认归属的历史计划任务 | 服务成功后才删除任务；删除失败时撤回新服务并恢复原任务 |
| 普通用户访问 | 无法写入安装 EXE、配置及全局工作/缓存/证据根；只获得当前任务所需目录权限 |

### 开发用真实 Guest 安装验收

此流程会停止 Agent、临时移走已确认归属的安装、创建模拟服务和任务。只能对获准的可还原测试 VM 执行。
没有许可、基础快照、匹配的发行包或可用的在线 Agent 时，不运行此流程。不要在宿主机直接执行 Guest 脚本。

构建 `SatsumaVmInstallRollbackProbe` 后，从源码根目录生成专用夹具（输出目录必须不存在）：

```powershell
python tests/make_installer_fixtures.py --agent <发行包/SatsumaGuestAgent-Install/SatsumaVM.exe> --probe build/windows-default/tests/Release/SatsumaVmInstallRollbackProbe.exe --output <专用夹具目录>
```

当前夹具生成器针对 0.3.4，派生 0.3.3、0.3.5 的版本资源及同版本不同哈希文件，并重新计算 PE 校验值。
这些文件只验证版本分支，不是真实历史或未来发行版，不能据此宣称所有历史配置均兼容。生产 EXE 不包含故障入口。

随后运行显式的 Host 驱动；`--vmx` 必须是已经授权的准确 VMX，`--snapshot` 必须来自用户确认的快照：

```powershell
python tests/real_vmware_installer_acceptance.py --host <发行包/SatsumaHost/SatsumaHost.exe> --fixtures <专用夹具目录> --vmx <获准VMX> --snapshot <基础快照> --output <新证据目录> --confirm DISPOSABLE_VM_INSTALLER_TEST
```

驱动创建测试前快照、恢复基础快照、检查 Agent，并通过受保护的一次性启动任务执行 Guest 安装矩阵。
运行安装矩阵时关闭测试 Host 网关；之后重新连接并收集结果，再以普通交互用户验证写权限。该流程当前要求
Guest 的 ProgramData 为 `C:\ProgramData`；环境不同会拒绝执行，不应改写系统目录来满足测试。
Guest 工作脚本核对硬件 UUID、目录、服务命令、原 EXE 哈希和夹具清单，拒绝已有同名测试目录或任务。
所有服务和文件变更限于已确认安装及本轮创建的夹具；没有运行锁时才恢复测试前快照，不强制清除异常租约。

驱动在新证据目录保存命令、实际退出码、原始输出、计划和 `summary.json`。成功时还保存
`installer-results.json` 和 `permissions.json`；失败时按 `collect-report.json` 指向的 active 运行读取已保留文件。
检查 `summary.passed` 之外，还必须确认 `restoration.status=restored`，并核对 VM 已关闭、测试 gateway 已退出。

这些 Python、PowerShell 和回滚探针只属于源码开发测试，不进入消费者发行包；Guest 消费者仍只使用单个 EXE。

## 任务、文件与恢复矩阵

- 同一 VM 的步骤串行、跨 VM 文件隔离；同名同内容和不同内容可用，同 VM 重复目标拒绝。
- SYSTEM 和普通用户混合步骤共享当前任务文件；普通用户不可获得全局目录写权限。
- 使用 UTF-8 JSON 和包含中文、空格的结果路径；对回传文件逐一核对 SHA-256。
- 本地 `SatsumaVmciFileTests` 覆盖 259、260、261、540 字符及超过一个 VMCI 分块的文件。
  真实 VM 长路径测试可使用 `tests/real_vmware_long_path_guest.ps1`，记录实际 Guest 和 Host 路径长度与最终字节。
  该脚本使用显式 Win32 文件 API，避免把 PowerShell 自身的路径限制误归到 Agent 上传链路。
- 脚本退出 0 但收集文件缺失时，报告应区分 `process_status=exited`、`exit_code=0` 与
  `evidence_status=collection_failed`，保留本地尝试证据，不能自动重新执行非安全步骤。
- 上传失败和完全失联分别测试。失败摘要只能在原 claim 有效时补发；完全失联可能保留人工门禁，不能伪造结果解锁。
- Host 编排进程崩溃后，用同一计划恢复；Agent 崩溃时，只有 `retry_safe=true` 才允许新 attempt，旧 owner 失效。
  终止 Agent 的夹具必须显式使用 SYSTEM，使其父进程为真正的服务；普通用户模式下的父进程是交互辅助进程，
  终止它不能作为服务崩溃的证据。
  已有 `tests/real_vmware_crash_recovery.ps1` 提供显式故障测试，运行前阅读[开发指南](开发指南.md)中的说明。
- 成功归档须能独立查询；失败证据按策略保留。结束时分别核对 Guest、Host 状态、归档、运行锁与电源状态。

## 人工界面验收清单

1. 在普通用户桌面双击首次安装 EXE，确认 UAC 由 EXE 发起。接受后，原 EXE 退出，仅管理员窗口继续显示结果。
2. 成功、已安装和失败窗口均有清晰中文说明，按 Enter 关闭。从已有 PowerShell 启动时，原终端应返回提示符。
3. 拒绝 UAC 后没有服务或目录变更，原窗口显示可理解的取消/失败原因。
4. 更新后重启 Guest，不再次双击 EXE，确认服务自动恢复，并能重新完成 Host `check`。

无法操作 UAC 安全桌面时，只将对应界面用例标为待人工验证，继续完成其余自动测试；不关闭 UAC，不降低权限来绕过确认。
