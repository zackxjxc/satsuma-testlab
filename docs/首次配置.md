# 首次配置

本文用于发行包首次落地。配置要求由 Satsuma 发行物和 Schema 定义；使用者 AI 可以协助发现环境、填写模板
和执行验证，但不能自行决定 VM 范围、猜测快照或代替用户授权管理员操作。

通过 AI 配置时，先让它读取发行包根目录的 `AI-START-HERE.md` 并加载
[`satsuma-testlab` Skill](../skills/satsuma-testlab/SKILL.md)。本文件面向用户解释完整配置过程；AI 的可执行
步骤、安全门禁和失败停止条件以同版本 Skill 为准。

## 职责边界

| 参与方 | 负责事项 |
|---|---|
| Satsuma 发行物 | 提供配置模板、Schema、字段说明、安装脚本和验证命令 |
| 使用者 AI | 只读发现 Host 环境，汇总缺失信息，按模板生成本机配置 |
| 用户 | 选择实验 VM、基础快照和 Host 状态目录，确认可能丢失 Guest 状态的操作 |
| Satsuma CLI | 校验配置、VMware、VMCI、Agent presence 和文件往返通道 |

## 需要确认的信息

Host 侧：

- `vmrun.exe` 的绝对路径；
- Host 归档目录、传输状态目录和 VMCI 端口；
- 每台实验 VM 的稳定 ID、VMX 绝对路径和期望 Agent 版本；
- 每台 VM 的只读基础快照，以及 Satsuma 快照前缀和数量上限。

Guest 侧：

- 默认连接 `vmci://2:42510`；只有特殊部署才需要覆盖 CID 和端口；
- VMware Tools 已安装并运行；
- 可使用管理员权限安装 LocalSystem Agent Service。

不需要手工选择日常工作盘。安装器优先验证本地固定 D 盘是否就绪、可写且至少有 2 GiB 空间，满足时使用
`D:\SatsumaTestLab`，否则回退到 `%ProgramData%\SatsumaTestLab`。桌面、临时目录、网络盘
和可移动盘不在候选范围。

VM、VMX 和基础快照属于用户授权边界。AI 可以读取本机已有路径和命令位置，但无法确认的值必须列为待确认，
不得使用模板占位值继续安装。

## 生成配置

已提供 VM 路径和基础快照的环境，可以直接让 Host 生成配置：

```powershell
bin\SatsumaHost.exe init --config config\lab.local.json --vmx "E:\VMs\Machine A" --vmx "E:\VMs\Machine B" --base-snapshot "Satsuma0.3.3"
```

`--vmx` 可重复使用，接受 VMX 文件或恰好包含一个 VMX 的目录；只登记这些明确选定的 VM。
`lab_id` 默认自动生成；`--lab-id` 可指定名称或兼容旧 Agent 的固定实验室。VMCI 端口默认为 `42510`，使用其他端口时加
`--vmci-port`，两端仍必须一致。命令自动查找 VMware 安装位置，也可通过 `--vmrun` 指定。

初始化会从 VMX 的 `uuid.bios` 生成硬件 UUID 和中性的 `vm-<uuid>` 标识，从同目录 `SatsumaVM.exe`
读取版本与 SHA-256，并查询基础快照是否存在。也可用 `--agent-binary` 明确选择同版本 Agent。
业务中的 gateway、client 等角色由消费者映射到这些 VM 标识；Guest 无需保存业务角色。
哈希来自交付的二进制，不能用 Guest 自报的哈希覆盖它，否则无法发现同版本不同构建混用的问题。

命令只创建新 JSON，不启动网关、不启动或恢复 VM。`initialized` 不等于 `ready`；仍需完成后面的
在线 `check`。配置旁的 `<配置名>.state` 和 `<配置名>.archive` 留给消费者运行时创建。
已存在的配置或非空状态目录会导致初始化失败，不覆盖既有环境。

此方式适用于具有独立 `uuid.bios` 的 VMware VM，不支持反射 Host SMBIOS 的 VM。克隆、移动后 UUID
改变时需要重新核对并登记；恢复到使用不同 UUID 的快照也必须重新验收。旧 Agent 在 `agent.json` 中
写死了 `lab_id` 时仍使用兼容模式；要改为通用 Agent，应移除外部安装配置后重新运行安装脚本，
或在本机配置中同时移除 `lab_id` 与 `vm_id`。通用模式不使用旧式绑定缓存。

尚无基础快照、需要不同 VM 快照策略或自定义目录时，仍可使用模板：

在发行目录使用 [Host 配置模板](../config/lab.template.json) 和
[Agent 配置模板](../config/agent.template.json)：

```powershell
Copy-Item config\lab.template.json config\lab.local.json
```

填写 `config/lab.local.json` 中所有 `REQUIRED` 和 `replace_with` 值。通用 Agent 登记前，Host 必须已填写
获准 VM 的 `hardware_id`，推荐直接由 `init` 从 VMX 生成。Guest 不需要用户提供 JSON；
高级部署可从 Agent 模板生成可选配置，用于覆盖端口等本机参数。

多 VM 实验需要在 `config/lab.local.json` 的 `vms` 中逐台声明。首次安装后由 Host 将发现的硬件 UUID 绑定到
这些稳定 VM 标识，不需要在 Guest 中手工保存 VM 标识。`init` 已经生成这些声明，无需重复手填。

## 安装 Agent

为目标 VM 准备一个本机安装目录（可通过只读 ISO、VMware 控制台或其他一次性介质传入），放入：

- `bin/SatsumaVM.exe`；
- `scripts/install-agent.ps1`；

把这两个文件放在同一目录，在 Guest PowerShell 中执行 `./install-agent.ps1`，或右键选择
“使用 PowerShell 运行”，确认 UAC。无需提前启动 Host 或携带 `agent.json`。
安装器自动选择存储目录、生成不含实验室和 VM 身份的本机配置。服务启动后持续等待 Host 登记。
成功、失败或取消 UAC 后保留结果窗口，按 Enter 关闭。没有 BAT 入口。

若 Windows 在脚本开始执行前就拦截它，脚本无法自行解除该拦截，可使用单次进程参数：
`powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\install-agent.ps1`，不更改长期执行策略。
自动化调用加脚本参数 `-NonInteractive`，关闭键盘等待；内部 UAC 重启自动携带本次执行策略参数。
脚本会创建 `<storage-root>/agent/bin`、
`<storage-root>/agent/agent.json` 和 `<storage-root>/work`，写回 `storage_root`，设置 SYSTEM 与
Administrators ACL，并注册 Windows Service；发行包自身仍是便携目录，不需要在 Host 安装。
安装结果会显示 Service 状态、启动类型、命令行和 Agent 版本；启动类型必须为 `Auto`。

### Guest 尚未初始化时

此时 Satsuma 通道本身还不可用，AI 不应要求用户先启用 Guest Account 控制通道、VMware Shared Folders、
网络共享或其他额外的长期传输机制。更直接的做法是由 AI 在 Host 上先准备一个完整的交接目录：放入
`SatsumaVM.exe` 与 `install-agent.ps1`。用户也可直接从发行包取出这两个文件复制到 Guest，不需要 AI
提前加工配置。只有特殊部署才附带可选 JSON；不要把旧实验室的 `agent.json` 混入通用安装目录。

AI 给出的人工接管说明应当可以直接照做，并清楚列出 Host 源目录、Guest 目标目录、管理员 PowerShell 中的
准确命令，以及表示成功的关键输出。安装脚本正常结束后，至少应核对 Agent 版本、Windows Service 状态和
启动类型；如果输出不符，用户应停止并把原始错误返回给 AI。AI 必须等待用户确认安装结果，再继续 Host 侧的
`discover`、`agent rebind` 和 `check`，不能仅凭文件准备完成就宣称 Guest 已初始化。

如果用户已有拖放、控制台挂载、一次性 ISO 或其他可靠复制方式，直接沿用即可。只有用户明确要求时，才有必要
协助建立共享目录等额外传输手段。

## 首次验收

Agent 安装后先启动 Host 网关，再启动目标 VM，在 Host 发现在线 UUID，并逐台确认 VM 标识：

```powershell
bin\SatsumaHost.exe gateway --config config\lab.local.json
```

保持网关运行，在另一个 Host 终端执行：

```powershell
bin\SatsumaHost.exe discover --config config\lab.local.json
bin\SatsumaHost.exe check --config config\lab.local.json --timeout-seconds 180
```

通用 Agent 先发送不带 `lab_id` 的 `enroll`，Host 根据配置中的硬件 UUID 白名单返回实验室及 VM 标识。
未登记的硬件会被拒绝，应先用 `init` 准备配置。旧式固定实验室 Agent 使用手工模板时仍可执行
`bin\SatsumaHost.exe agent rebind --config config\lab.local.json --vm vm_01 --hardware-id <uuid>`。

`agent rebind --hardware-id` 会把 UUID 写入 `lab.local.json`，并在 Host 状态根发布绑定记录；Agent 在下一轮
轮询中采用该 VM 标识，无需重装 Service。多台未绑定 Agent 同时在线时，先通过 VM 电源状态或逐台启动确认对应关系。

首次 VMCI 通道连通后，Agent 会发布 inventory。验收时 `check` 先验证/刷新 inventory，再执行内部 echo；需要
查看或更新快照时使用：

```powershell
bin\SatsumaHost.exe agent inventory --config config\lab.local.json --vm vm_01
bin\SatsumaHost.exe agent inventory refresh --config config\lab.local.json --vm vm_01 --timeout-seconds 180
```

只有顶层 `status` 为 `ready` 才能发布业务任务。失败时按 `checks` 和 `agents` 字段处理配置、VMware Tools、
VMCI 网关或 Agent 问题；不得仅因为 VM 能启动就宣称环境已经可用。

## 制作基础快照

| 快照类型 | 命名规则 | 可配置为 base | AI 可创建 | AI 可删除 |
|---|---|---:|---:|---:|
| 用户基础快照 | 不使用配置的 `ai_prefix` | 是 | 否，需用户确认 | 否 |
| Satsuma AI 快照 | 使用配置的 `ai_prefix` | 否 | 是 | 是，仅限同前缀 |
| 外部快照 | 其他未登记名称 | 否 | 否 | 否 |

AI 快照可以由任务显式用于 `restore_before` 或成功/失败恢复，但不能登记为 `vms[].snapshots.base`。验证完成的
AI 快照若要提升为基础快照，应在 VM 已关机且用户确认后重新创建或重命名为不带 AI 前缀的用户快照，再更新
配置；不要绕过前缀检查。达到 `max_ai_snapshots` 时先列出现有 AI 快照并由用户决定保留范围，不删除用户或
外部快照。

通用冷快照可在 Agent 安装、Service 状态和版本检查成功后制作，此时无需连接具体实验室。
它表示“已安装、待登记”，不能宣称已通过在线验收；消费者启动 Host 后仍必须完成 `check`。
制作冷快照时先正常关闭 Guest，确认
VMware 显示虚拟机电源已关闭，再创建带 Satsuma 版本号的快照，例如 `Satsuma<版本>_Cold`。安装 Agent 之前
制作的快照不包含 Service，恢复后不会自动上线，不能作为编排基础快照。

暖快照会保存运行内存和当时的 Agent 会话，只适合明确需要恢复运行态的测试；恢复后仍必须取得本次新建的
diagnostic echo 结果，不能只把 Host 状态根中的旧 presence 当作上线证据。多台未绑定 Agent 无法从现有
presence 可靠推断 VMX 对应关系时，应逐台启动确认，不使用 Guest IP 猜测硬件身份。

## 向消费者交付环境

交付内容是匹配的完整发行包、针对本机的 `lab.local.json`，以及说明 VM 范围、快照和权限的环境文档。
TXT 可以提供生成配置所需的信息，但 CLI 实际读取 JSON；发行包与环境配置可以分别交付。

交付时关闭验证用的 Host 网关，结束测试并确认租约已释放，VM 保持关机冷基线。
消费者自行启动网关及获准控制的 VM，再执行 `check`。Host 尚未启动时，Agent 会持续重试连接。
不要把旧运行的 `state`、`archive`、遗留租约作为新发行包的必要附件，也不要通过删除未终结状态来清场；
先使用正常完成/恢复流程结束旧运行。要创建完全独立的消费环境，可用新的配置文件名重新执行 `init`。
